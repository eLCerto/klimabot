# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the **Samuel Malíšek Klimabot** — a chatbot tailored for Samuel Malíšek Klimabot. Samuel Malíšek Klimabot sells only Samsung and Toshiba (RAS residential, RAV commercial). No other brands.

## Running the bot

```bash
bash setup_project.sh          # creates .venv and installs deps from pyproject.toml (--recreate starts fresh)
source .venv/bin/activate      # Git Bash on Windows: source .venv/Scripts/activate
python main.py                 # web app on http://127.0.0.1:5000 (runs web/web.py)
python bot.py                  # interactive CLI (type 'bye' to quit)
python cost_report.py          # token/cost summary across data/logs/*.jsonl
make build / make web / make down   # the web app in Docker on http://127.0.0.1:7860 (docker compose)
```

**Repository layout.** `bot.py` (the whole bot, one file on purpose), `main.py` (starts the web app) and `cost_report.py` (imported by `web/web.py` and the tests) stay in the root; the Dockerfile too, because Hugging Face Spaces build from the repo root.

```
config/      discounts.json, consent_phrases.json, sizing_policy.json, stock_policy.json, model_prices.json, filtration_policy.json
knowledge/   samsung/, toshiba/, montaz/ (price lists) and rules/ (behavior rules) — everything retrieval reads
web/         web.py + static/ (index.html, vendor/)
tests/       test_guards.py
eval/        run_eval.py, analyze.py, test_scenario.py, scenarios/, runs/ (gitignored)
docs/        screenshot
data/        runtime output, gitignored (KLIMABOT_DATA_DIR): logs/, sessions/, handoff_records/, leads, caches
```

`bot.py` finds them through `CONFIG_DIR`, `KNOWLEDGE_DIR` and `DATA_DIR`; chunk sources are stored with `/` (`knowledge/rules/…`) on every OS.

Requires `ANTHROPIC_API_KEY` in `.env` (see `.env.example`). The bot raises `SystemExit` on missing key.

**Docker** (`Dockerfile`, `docker-compose.yml`, `.dockerignore`; README → Docker): one container, one process. The image installs the CPU-only PyTorch, puts both models into `HF_HOME=/opt/hf` (then `HF_HUB_OFFLINE=1`) and builds the KB embedding cache into `/app/.kb_cache` by running `import bot` with a dummy key and a throwaway data dir — so any change to `bot.py`'s import-time behavior must still work with no `.env`, no network and no mail settings. It runs as uid 1000 (Hugging Face Spaces), with `KLIMABOT_DATA_DIR=/data` as the volume and port 7860. `web.py` turns SIGTERM into a clean exit that ends open conversations (mailing their leads), hence `stop_grace_period: 60s`. The app's port is published on 127.0.0.1 only and compose sets `KLIMABOT_TRUSTED_PROXIES=1`. On a server, the `caddy` service (compose profile `https`: `COMPOSE_PROFILES=https` + `KLIMABOT_DOMAIN` in `.env`; `Caddyfile`, image pinned by digest) terminates HTTPS with Let's Encrypt and proxies to `klimabot:7860`. It has no `encode` (it would hold back the event stream), and it replaces the client's `X-Forwarded-For`, which is the one hop `web.py` trusts. That VPS + Caddy setup is the recommended public deployment (README → Docker → On a server).

First run downloads two HuggingFace models (~750 MB total): `intfloat/multilingual-e5-base` (embeddings) and `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` (reranker). The reranker is loaded lazily on the first `search_knowledge` call.

`tests/test_guards.py` (stdlib `unittest`, run with `.venv/Scripts/python -m unittest discover -s tests`) covers the guarantees that live in code: consent, redaction, lead routing, the output gate, `max_tokens`, price provenance, the fit check, the audit, the spend caps and API-error handling, the size caps, and the web demo's limits (Flask test client). The model is replaced by a `FakeClient` that replays scripted responses or raises scripted SDK errors, and fails on any `tool_use` sent without its `tool_result`; no key or network needed, but importing `bot` loads the embedding model. On Windows set `PYTHONIOENCODING=utf-8` when the output is piped (the bot prints Slovak text). `eval/run_eval.py` raises the spend caps by default (the CLI's usage figures carry its own overhead); set `KLIMABOT_SESSION_USD_CAP` to test them. There is no linter config and no build step. `eval/test_scenario.py <name>` drives a scripted conversation through the live API (needs the key) and prints the transcript with validator events; it makes no assertions. `eval/` runs scripted customer conversations with the local Claude Code CLI (`eval/run_eval.py --scenarios …`, then `eval/analyze.py <run dir>`), or with `--api` against the real API with the production caps on and a run budget (`--budget-usd`, default 10; the key must be real — bot.py refuses the `.env.example` placeholder). `eval/scenarios/boundaries.json` covers the boundaries (off-topic, medical, "are you human", staff data, smoke, English sparks); a scenario's `must_say` (`[{"turn": 1, "pattern": "112"}]`) requires a pattern in that turn, next to `must_not_say`. `eval/scenarios/abuse.json` holds the cost-abuse conversations (tool-loop injection, 50-code compare, long message, state stuffing, handoff spam, a 24-question marathon). `analyze.py` reports cost per conversation (from the `llm_turn` events), the cache-read share, conversations that hit the cap and each scenario's `max_usd`. The bot is a single-file CLI (`bot.py`) with a Flask web app (`web/`).

## Architecture

`bot.py` is an intentionally flat ~3,900-line monolith — the whole agentic pipeline reads top-to-bottom in one file. The rough order is: config + `Session` → logging with redaction → pricing policy load + product index → fit check + pricing (`quote`) → other tool implementations (incl. session persistence + handoff Markdown renderer) → tool schemas → KB load/embed/index → retrieval pipeline → tool dispatch → conversation summarization → post-reply validator → output gate → language & consent → system blocks → turn loop + REPL. When changing behavior, locate the section by header comment; don't try to refactor into modules — the user wants it readable as one file.

### Knowledge base pipeline

Everything retrieval reads lives in `knowledge/`: two brand DBs (`samsung/`, `toshiba/`) + a brand-agnostic installation accessories cennik (`montaz/`) + one rules dir (`rules/`). **Only Samsung and Toshiba are sold** — competitor DBs were removed when this bot was tailored for Samuel Malíšek Klimabot. `knowledge/rules/` contains Slovak `feedback_*.md` behavioral rules (with `RULES_INDEX.md` as an index) and gets `+0.3` in `authority_bonus()` (it matches the `knowledge/rules/` source prefix).

Each brand directory is split into category subfolders; `montaz/` is flat (one cennik per category isn't needed for installation parts):

```
knowledge/
  samsung/
    single_split/      rac.json
    multi_split/       fjm.json
    light_commercial/  cac.json
    accessories/       accessories.json
    glossary.json      SAMSUNG_INDEX.md
  toshiba/
    single_split/      ras_single.json
    multi_split/       ras_multi.json
    light_commercial/  rav_outdoor.json, rav_indoor.json
    accessories/       ras_accessories.json, rav_accessories.json
    ras_glossary.json  rav_glossary.json
    TOSHIBA_INDEX.md   RAV_INDEX.md
  montaz/
    cennik.json        glossary.json  MONTAZ_INDEX.md
  rules/
    feedback_*.md      RULES_INDEX.md
```

`load_chunks()` recurses through `<brand_dir>.rglob('*')` and tags every chunk with a `Kategória: single-split | multi-split | light-commercial | accessories` line derived from the path. This lifts BM25 recall on category-defining queries (e.g. "potrebujem multi-split do 3 izieb") so the model is much less likely to mix single-split and multi-split candidates. `_category_from_path()` maps the path segment to the human-readable tag via `CATEGORY_FOLDERS`. `montaz/` items don't get a Kategória tag (they don't sit in a category folder) — the bot finds them via BM25 keyword match on the cennik glossary aliases (silentblok → AV kits, antivibračná konzola → DXL series, etc.). Glossaries live at the brand-dir root and are discovered by `_build_alias_map()` via `rglob('*glossary*.json')`.

The montáž cennik is **not** subject to `discounts.json` and `quote` doesn't price its items (they use `kod`/`cena_EUR`, not the indexed code fields). The bot uses it only to explain what an installation includes. **The bot never states an installation price** (the owner's decision: it depends on the specific installation) — the PM prices it after the free site visit.

Per-file chunking strategy: `chunk_json_file()` emits one chunk per top-level dict key; `.md` files split on `\n\n`. After chunking, each chunk is prefixed with the `Kategória:` line and then passes through `expand_chunk_with_aliases()`, which appends a `Synonymá: ...` line built from the brand glossaries so BM25 can match SK/CZ/EN variants of the same term.

Retrieval is hybrid: BM25 (with diacritics-folded token variants so "klimatizacia" matches "klimatizácia") + cosine over e5 embeddings, fused via reciprocal rank fusion (k=60), top-25 candidates → cross-encoder rerank with authority bonus → top-K. K is dynamic: model code regex hit → 3, query <5 words → 8, default 5. The model can override via the tool argument (capped at 10).

Embeddings cache to `.kb_vecs.npy` with a sha256 fingerprint in `.kb_hash.txt` (in `KLIMABOT_KB_CACHE_DIR`, default the data dir; a failed write is only printed, so a read-only cache in the image can't stop the bot) that **includes `EMBED_MODEL_NAME`** — swapping the embedding model auto-invalidates the cache. Don't add a manual cache-clear step.

e5 requires asymmetric prefixes: `encode_passages()` prepends `passage: `, `encode_query()` prepends `query: `. Don't drop these — recall collapses without them.

### Agentic loop

The system prompt forbids the model from answering product/price/feature questions without first calling `search_knowledge`, and forbids manual price math — `quote` is the only source of any euro amount (see Pricing rules). There is no always-on KONTEXT block; retrieval is fully tool-driven.

Tool dispatch is all in `dispatch_tool()` returning `(content_str, is_error)`. `run_user_turn_streaming()` drives a tool loop: call the model (`_call_model()`, **not streamed**, `max_tokens` 2048) → sanitize + gate the text → emit it → if `stop_reason == "tool_use"`, run every tool_use block, append a single user message containing all tool_results, loop. `is_error: True` on a `tool_result` lets the model recover instead of silently using a bad value. **Text written next to a tool call is neither shown nor stored** (the owner's decision: one bubble used to stack 3–7 drafts); the answer comes after the tool (`tool_text_hidden` is logged). Exception: a complete reply (`_complete_answer`: no narration, a question or ≥ 160 characters) whose only tool is `update_customer_state` is the answer — the tool runs right away, the reply is stored without the tool call, and the turn ends without a second call. A price question the model leaves without a quote (`cena-neodpovedana`) regenerates with `tool_choice: any`, so the next attempt must call a tool. A response cut off at `max_tokens` is retried once with 4096; if it is still cut off, its tool_use blocks are dropped — a `tool_use` without its `tool_result` would break every later API call of the session.

**Spend caps — in code, before every call.** Every call is priced from `model_prices.json` (`usage_cost()`; `_record_usage()` charges it to `S().cost_usd`). Before a call, `budget_for_next_call()` compares that call's worst case (`projected_call_cost()`: the latest main call's context + 6k tokens — HyDE and summary calls don't move that base — all written to the cache, plus every output token) with what is left of the customer message (`TURN_USD_CAP`, $0.40) and of the conversation (`SESSION_USD_CAP`, $0.50; env `KLIMABOT_TURN_USD_CAP` / `KLIMABOT_SESSION_USD_CAP`). When only one more call fits — or the turn reaches `TURN_MAX_CALLS` (10) or `TURN_MAX_SECONDS` (180) — that call is made with `tool_choice: none`, so the customer still gets an answer (a tool_use returned anyway is dropped). When nothing fits, code writes the closing message without a model call (`_landing_text`: a recap of the last `quote`, `COMPANY_CONTACT`, "start a new conversation") and the conversation stays closed (`limit_reached`). Tools are bounded too: `RESPONSE_MAX_TOOL_CALLS` (6) per response, `TURN_MAX_TOOL_CALLS` (16) and `TURN_MAX_SEARCHES` (3) per turn (the reranker takes about 9 s per search on the demo server's 2 cores; the second search of a turn gets a nudge in its result, and only one search runs per response — searches asked for together are issued before any result is seen, so the rest get an `is_error` result, `limit_hit` `response_searches`) — over the cap the tool doesn't run, but its tool_use still gets an `is_error` tool_result telling the model to answer. A regeneration is allowed only while the budget, with the rejected draft counted, leaves room for an answer after it; HyDE and summarization skip themselves when the conversation budget can't take them. At 80 % of the conversation budget the SERVER block asks the model to wrap up. The limits are per conversation and don't stop anyone from starting a new one — that is `web.py`'s job (per network and per day).

**API errors** (`_call_model()`; the SDK's own retries are off): a 429 with a short `retry-after` (≤ `API_MAX_RETRY_AFTER`, 10 s) and 5xx / 529 / connection errors are retried at most twice; anything else ends the turn with a generic message (`_ERROR_REPLY`, never the raw error) and rolls the turn back. A spend-limit error is never retried: the account's monthly cap (429 `enforced_spend_limit_reached`, paused until the 1st of next month UTC) or our own Console limit (400 "reached your specified …", retried after 30 min) opens a process-wide breaker saved to `.spend_breaker.json`. While it is open every turn gets a code-written "temporarily unavailable, write to us" reply and the API isn't called.

**The output gate: replies are checked before the customer sees them** — every response, tool-calling ones included (their tools haven't run yet, so regenerating them is safe). `sanitize_reply()` fixes mechanical issues (headings, `---`, extra emoji, common Czech words in Slovak sessions) and `_canonicalize_consent_question()` rewrites any consent question to the canonical wording. `validate_assistant_reply()` then sorts violations: **HARD** ones sit inside one sentence (`_HARD_RULES`: an amount `quote` didn't produce, `~`/`cca`/`approximately` before an amount, an invented model code, a permit promise, a question where the outdoor unit goes, a budget-fit claim no `quote` budget check supports, internal reasoning or tool names shown to the customer, a callback promise or "zaznamenal som" before consent, a promised delivery/installation date or a judgement that the customer's date is realistic, a quote amount shown under another product's name (`cena-iny-produkt`, `_misattributed_amounts`), an amount labelled with the wrong DPH basis (`dph-zamena`, `_vat_mislabeled_amounts`), a catalog code called "not in the price list" (`mimo-katalogu`), SEER/SCOP/dB figures no tool returned or savings / payback claims, with or without a figure — "ušetrí peniaze na elektrine", "nižšie náklady na elektrinu" (`nepodlozene-udaje`, `_SAVINGS_CLAIM_RE`), a contact request in a complaint (`reklamacia-kontakt`), a claim to be a person (`ai-identita`, `_HUMAN_CLAIM_RE`; "nie som človek" is fine), an energy class the price list doesn't give the named series, or a filtration claim against `filtration_policy.json` — a tier 1–2 series with a "štandardný / základný filter", a tier 2+ one with "najlepšia filtrácia" (`nepodlozene-udaje` too, `_wrong_energy_classes`, `_wrong_filtration_claims`; `_series_fragments` reads a heading as naming the series for the list under it and a table cell by its column's header; a flagged table row is cut whole — AR35 was called "E/D", Avant S2 got "Štandardný filter" in a table), a wall-only series called a cassette (`typ-jednotky`, `_wall_called_cassette`), a brand's trademark in a sentence about the other brand (`brand-funkcia`, `_brand_term_mixups`: WindFree / Tri-care / Freeze Wash next to a Toshiba series, HADA / plasma ionizer / Ultra Pure next to a Samsung one; sentences naming both brands and negations pass), a stock claim — "skladom", "hneď dostupný" — for a product whose quote `availability` isn't stock, or before any quote for Samsung, whose availability the PM confirms (`sklad-tvrdenie`, `_false_stock_claims`: the product named in the sentence, else its paragraph)). They get up to `MAX_REGENS_PER_TURN` (2) regenerations per customer turn with per-rule instructions (`_regen_note`, never "keep the same content"); whatever still violates is cut out sentence by sentence (`_drop_hard_sentences`). **REGEN-ONLY** problems cover the whole reply (`_REGEN_ONLY_RULES`: a reply largely in Czech; a direct price question left without a quote although the size or the exact codes are known; a request for contact details or the town before any price, `kontakt-pred-ponukou`; an empty final reply when nothing was shown this turn, `prazdna-odpoved`; the conversation's first offer showing one priced option when the customer named no model or series, `dve-moznosti`, `_single_first_offer` — the owner wants two to choose from, and like `cena-neodpovedana` its regeneration must call a tool; before the first quote, a question about the preferred brand, or about the budget once the size is known, `zakazana-otazka`, `_forbidden_questions` — its regeneration must call a tool when the size is known) — regenerated, never cut. A final reply that is still empty gets `_EMPTY_REPLY_FALLBACK`: the customer never gets silence. After a cut, lines left with only a list marker, emoji or punctuation and a closing heading are removed (`_tidy_after_cut`). An approximation marker in front of an amount `quote` returned exactly is simply removed (`_strip_exact_approx`) instead of costing a regeneration. Everything else is **SOFT**: fixed mechanically where safe (the recycling-fee mention, Cyrillic letters transliterated, CJK characters and citations of non-existent files removed, a sentence listing two or more outdoor placement options dropped (balkón, fasáda, strecha, záhrada, dvor, garáž…), "s DPH a recyklačným poplatkom" / "s DPH a poplatkami" rewritten to "s DPH, bez recyklačného poplatku" — the fee is always on top — "(približne)" after an amount removed, and a Wi-Fi claim under a series without Wi-Fi as standard (`_fix_wifi_claims`, `_series_without_wifi`: SEIYA, SEIYA Classic 2, the Toshiba console — the nearest series named on that line or above, reset by another brand or two series) completed with "— iba s voliteľným Wi-Fi modulom za príplatok", a "v základe" on that line removed), otherwise only logged. Each of these rules exists because the round-2 eval caught the model doing it. The conversation history stores exactly the text that was shown. `_drop_narration` / `_NARRATION_RE` now only decide whether a bookkeeping reply is complete (narration = an announced next step, so the loop continues). Only then is the text emitted as a single `token` event, so a rejected draft never reaches the browser. Don't reintroduce token streaming without keeping that guarantee.

All per-conversation state lives on a `Session` object (`conversation`, `customer_state`, `input_tokens`, `handoff_path`, `compat_checked_outdoors`, `user_inputs`, `quotes`, `gdpr_question_asked`, the consent fields `consent_ask_index` / `consent_ask_purpose` / `consent` / `consent_refused`, `support_handoffs`, the spend fields `cost_usd` / `last_call_input` / `limit_reached`, the per-conversation counters `lead_calls` / `auto_capture_attempts` / `handoff_calls` / `consent_reasks`, `lead_record` / `lead_mail_queued` for the PM mail, `network` (set by the web app), its own `log_path`). `user_inputs`, `quotes` and the consent fields cover the whole session on purpose — `maybe_summarize()` shortens `conversation`, and the price check, the consent guard and the handoff must not lose anything when it does. Bot functions reach the active one via `S()`, which reads a `contextvars.ContextVar` set by `use_session()`. The CLI uses the default session created at import; the web app activates the visitor's session at the start of each request. Never reintroduce module-level conversation state — concurrent web visitors would share it. A thread that never called `use_session()` gets a `LookupError`, not someone else's session.

The customer state (`S().customer_state`, still called CUSTOMER_STATE in comments and tool descriptions) is mutated by `update_customer_state` (deep-merge: lists union, `None` removes keys; `updates` sent as a JSON string is parsed, trailing junk ignored — the model does that sometimes; it returns only the changed field names and drops writes to `consent_*`) and by code for consent and the phone/e-mail safety net. **Prompt caching and the server context.** A request is tools → system → conversation → server context. `build_system_blocks()` returns only the persona prompt and the `CRITICAL_RULES_TEXT` checklist, identical on every call, with a cache breakpoint on the checklist. `_messages_for_api()` sends the stored history the same way every call (customer text as a text block) with a second breakpoint on its last block, so each call reads the conversation the previous call cached. Everything that changes per call — the customer state, the filtration ranking, the industrial-space note, a request to ask what matters to the customer before the first offer (while no quote exists, the m² is known and `_preferences_known()` is false: no wish for quietness, filtration, Wi-Fi, design or a low price, no named series or code, and no feature question asked yet — or, when the latest message asks for a price, to price two options first and ask after) (compact JSON, headed as data written from the customer's words, not instructions), the consent status, a note when the customer just picked an offer ("Toto chcem", "beriem tú", `_OFFER_CHOSEN_RE`: ask for the contact, the next step only as a condition — the gate rejected "ozve sa" twice per click), the session language (English customer → English replies), the 80 % budget note and a regeneration note — is `build_server_context()`: a `<server_context>` text block appended to the final user message after the breakpoint and never stored in the history. A tag the customer types is defused (`<server-context`), the checklist tells the model the block is the server's, and the validator flags it in replies. The eval's CLI adapter renders the block as is. Because the state is re-sent on every call, `update_customer_state` clips strings to `STATE_MAX_STRING` (300) and lists to `STATE_MAX_LIST` (20), and refuses an update that would take the whole state over `STATE_MAX_CHARS` (4 000). `discounts.json` is deliberately **not** in the prompt — percentages the model can see are percentages it is tempted to apply itself. The segment triggers it needs are generated into `quote`'s tool schema by `_segment_guide()`.

`update_customer_state` has an **explicit canonical field schema** (30+ fields with `enum` constraints for `place_type`, `usage`, `segment`, `predpriprava`, etc. — see the tool schema for the full list). `additionalProperties: true` is still set so the bot can add ad-hoc fields, but only canonical names render into the structured handoff Markdown sections — unknown fields are silently dropped from the PM brief. After each successful mutation, the state is **atomically persisted** to `sessions/<session-log-stem>.json` (tmp file + rename) so a crash mid-conversation doesn't lose discovery context. Personal data (`_PII_FIELDS`: `lead_name/phone/email/obec`) stays in memory only until code records consent — `_storable_state()` strips it from `sessions/` and `handoff_queue.jsonl`, and `log_event()` masks phone numbers, e-mail addresses and every known `lead_*` value in **every** event before consent. The server's own text — `COMPANY_NAME`, the company contact and the canonical consent questions — is never masked (`_PII_PROTECTED_RE`): the audit needs the question verbatim even when the customer is called Samuel. A name typed before the bot knew it is masked by `_scrub_session_log()` when the customer refuses or the session ends without consent (`end_session()`, called by the CLI, the eval harness and the web app on reset / idle eviction). `_auto_extract_lead_info()` copies only a phone number or e-mail into the state (names and towns are not guessed) and logs field names, not values; the capitalised words typed next to the contact ("Dobrý deň, Jozef Mráz, 0907…") go to `pii_seen` so the log masks them anyway. Names and towns of 4+ letters are masked with their Slovak case endings ("Nitra" also masks "v Nitre", `_pii_pattern`; case-sensitive, so the colour "biela" survives "Biely").

### Lead handoff workflow

When a customer picks a model and gives consent, `capture_lead(name, contact, summary, interested_in)` does two things, and the end of the conversation a third:

1. Appends a JSONL line to `leads.jsonl` (machine-readable record + customer_state snapshot).
2. Renders a **human-readable Markdown brief** to `handoff_records/<session-log-stem>_<slug-name>.md` for the project manager (one file per conversation, overwritten when the lead is corrected).
3. **E-mails the final brief to the PM when the conversation is finished** — `end_session()` → `_mail_lead_to_pm()`: one plain-text mail per conversation (the brief as the body, corrections included), to `LEAD_MAIL_TO` over SMTP (`SMTP_HOST`, `SMTP_PORT` 587 STARTTLS / 465 SSL, `SMTP_USER`, `SMTP_PASSWORD`, `LEAD_MAIL_FROM`; off unless `SMTP_HOST` and `LEAD_MAIL_TO` are set, a bad setting stops startup). Finished means the CLI's `bye`, the web Reset, the tab closing, an idle web session or the web app shutting down. One background worker sends the mails (`_MAIL_WORKER`), so a slow server holds nobody up; a dropped connection or 4xx is retried twice, anything else is logged as `lead_mail_failed` — the lead is still on disk. No mail after the customer asked to withdraw consent (`consent_withdrawal_requested`); one mail per contact per `LEAD_MAIL_DEDUPE_DAYS` (7; phones compared by their last 9 digits, hashed in `.lead_mail_sent.json`); at most `LEAD_MAIL_MAX_PER_NETWORK_DAY` (3) per network a day (`Session.network`, set by the web app) and `LEAD_MAIL_MAX_PER_DAY` (30) in total. On a public page anyone can type someone else's phone, so the web demo also sets `LEAD_MAIL_DEMO`: the subject starts with `[DEMO]` and the body with a warning that the details may be made up. Mail goes only to the configured addresses, never to one typed in the chat; the subject is one line, so chat text can't add headers. The eval harness and the tests blank `LEAD_MAIL_TO` before importing `bot`.

A `quote` made after the lead refreshes it in code at the end of the turn (`_refresh_lead_brief`: the record's quotes and state, a new leads.jsonl line, the brief rewritten with the latest variant marked "posledná ponuka zákazníkovi", a `handoff` event, `handoff_refreshed`), so a customer who switches models after consent doesn't leave the PM the old offer when the model skips `capture_lead`.

The Markdown's structured sections (Zákazník, Záujem, Priestor, Inštalačné prostredie, Predpríprava, Pre PM – cenové ponuky, Zdroj) are **auto-rendered from `CUSTOMER_STATE`** via `_render_handoff_sections()`, except the prices: "Pre PM – cenové ponuky z rozhovoru" lists every distinct `quote` result of the session (`_render_quotes()`: lines with availability, totals, recycling fee, "Montáž: určí PM", the budget status, fit warnings and the cheaper alternative), so the PM sees exactly what the customer was quoted. The brief also renders `notes`, the heat load (from the customer's own kW when the model stored none), rack count, 24/7 and redundancy; the segment is never assumed "retail" — without a stored one it is "B2B_firma (podľa zákazníka)" when the customer wrote IČO / s.r.o. / "na firmu" (the IČO is rendered too), else "neuvedené". The leads.jsonl record carries the same `quotes`. The bot's `summary` argument is therefore **prose-only**: it goes into the "Otvorené otázky pre PM a poznámky" section and is meant for sentiment notes, recommendation rationale, and unresolved questions. Missing canonical fields degrade gracefully to `"neuvedené"` — there is no hard validation, the bot doesn't re-ask if discovery was abbreviated. `summary` sentences claiming the offer fits the budget without `quote` support are dropped. When the customer's last message says "lacnejšiu" and two or more variants were quoted, `capture_lead` refuses a lead naming the dearer one. The auto-capture summary includes the customer's last messages, so the PM sees the request even when the model stored nothing. Helpers: `_state_get(state, *keys, default)` tries multiple alias keys (canonical English + Slovak fallback), `_fmt_value(v, fmt=None)` formats booleans (`Áno`/`Nie`), lists (comma-separated) and m²; `_eur()` formats euro amounts the Slovak way (`1 290,50 €`). See [knowledge/rules/feedback_handoff_zapis_z_rozhovoru.md](knowledge/rules/feedback_handoff_zapis_z_rozhovoru.md) for the bot-facing rule.

**Consent is decided by code, never by the model** (section "Language & consent" in `bot.py`). The canonical question — sales only, Slovak and English, naming name, phone, e-mail, town and the chosen model — and the yes / no vocabulary live in `consent_phrases.json`, read by `bot.py`, `cost_report.py` and `eval/analyze.py` alike; earlier wordings (without e-mail, and the retired support question) are in `previous_questions`, which the audit still recognises. When a reply asks for contact details (`_asks_contact`: `_CONTACT_REQUEST_RE` after blanking a phone as a device — "ovládanie cez telefón", "telefónom", `_PHONE_AS_DEVICE_RE`), or contacts arrive without a consent answer, code appends the canonical question (English sessions get the English sentence plus the Slovak one); a paraphrase the model writes is rewritten to it. Only the customer's **very next message** after the latest question can give consent (`_process_consent_reply`): an explicit yes (`yes_re`, minus "súhlasím s cenou"-style phrases in `yes_not_consent_re`) records `S().consent` with purpose, timestamp and the customer's words; "OK / beriem / môžete" don't count, and neither does a "súhlasím" typed before the question. An explicit refusal (`no_re`, incl. "kontakt vám nedám") counts at any time and wins over a yes in the same message; disagreeing with the price, the offer or a model (`no_not_refusal_re`: "nesúhlasím s cenou", "to nesúhlasí") is not a refusal — in `bot.py` and in both audits. When contacts are known and the customer answered the question with something other than yes / no ("S tou cenou súhlasím", a stock question), code asks again — at most twice per conversation (`consent_reasks`) — and the server context tells the model what to say meanwhile (thank, explain the explicit yes is needed, promise nothing). A paraphrase of the question written as a statement is removed. After a refusal or "ozvem sa sám" code adds the company contact if it wasn't shown recently. In the web chat the question comes with two buttons (`CONSENT_QUICK_REPLIES`, the `quick_replies` event): they send the explicit words "Áno, súhlasím" / "Nie, nesúhlasím" ("Yes, I agree" / "No, I don't agree") as the customer's message, so consent is still decided by code from that message and the audit reads it from the log as before (a test checks that the bot and both audits read every button the same way). `capture_lead` refuses (tool error, the model recovers) unless (a) consent with purpose `sales` is recorded and (b) every model code in `summary` / `interested_in` appears in the conversation or a session quote.

Complaints (the owner's decision): **the bot doesn't handle complaints, repairs, refunds or legal questions.** A conversation is a support case (`_support_case()`) when the customer complains (`_COMPLAINT_RE`, or a fault in a unit "you installed") or `request_human_handoff` got a support reason — and stops being one once a sale starts (a `quote` exists). In a support case no consent question is asked, a contact request in the reply is a HARD violation (`reklamacia-kontakt`), and code appends the company's e-mail / phone (`_complaint_contact_text`, `COMPANY_EMAIL` / `COMPANY_PHONE`). `request_human_handoff` still records the request in `handoff_queue.jsonl` (without personal data) and tells the model to promise nothing. Its `purpose` is required; the fallback guess (`_SUPPORT_REASON_RE`) uses whole complaint terms only, so "installer", "vrátane" or "podporuje" stay sales. "Reklama" (an advert) isn't a complaint and "novú od vás" isn't a unit we installed (`_COMPLAINT_RE`, `_OUR_INSTALL_RE`).

GDPR refusal path: if the customer refuses, code records `consent_refused`, masks the personal data known by then in the whole session log (`_scrub_session_log`) and drops the `lead_*` fields from the state; the bot **does not call `capture_lead`** — no JSONL line, no Markdown file. It gives the customer the direct contact (`COMPANY_CONTACT`) and offers an in-chat recap. See sekcia 3 and 6 of the handoff rule.

### Pricing rules

The model never handles a price as input. `quote(items=[{code, qty}], segment, budget_eur, promotion_code)` takes model codes only and does everything else in code: looks up catalog prices, maps each product to its discount category, adds the segment modifier and an active, in-date promo (`active_promotions.promotions[]` matched by `code` + `applies_to` category), caps at `max_total_discount_pct` (the cap is never put in front of the model), and returns line items (incl. `unit_discount_eur` and `availability` from `stock_policy.json`), totals, `DPH_23pct_eur`, totals with DPH, the `recycling_fee_per_unit` (with the number of units), an `installation` note (no figure), a budget comparison (`budget.status` in the wording of the matematicka-kontrola rule, on the customer's basis: units with DPH unless they said "bez DPH", `compared_price_eur`; `budget_includes_installation` when their budget covers installation — then only the units can be said to fit), `comparison_with_earlier_quotes` (signed differences and which is cheaper) and `cheaper_alternative` (a cheaper suitable single-split set when the customer named no series; for a multi-split, the same outdoor unit with the cheapest same-size wall indoor units of its price list, Wi-Fi as standard if wished, as `items`, `_cheaper_multi_indoors`). **No installation price exists anywhere** — not in `discounts.json`, not in `quote`, so any installation figure in a reply fails the provenance check. Every successful result is appended to `S().quotes`. A sanity guard rejects any unit price below 55 % of catalog as a policy-data bug — preserve it.

**Fit check** (`_fit_check`, thresholds in `sizing_policy.json`; rules point there instead of restating numbers): the place and the heat load are read from what the customer typed, never from model-written state. A server room, salon or medical practice named by the customer + residential lines is an **error**; a server room also needs ≥ 2 independent systems (no Twin/multi), each with cooling ≥ `capacity_factor_per_system` × the stated kW, plus the brand's failover controller. Cassettes are refused when the customer said there is no suspended ceiling. The model may pass `override_reason` when the customer insists, which turns these errors into `fit_warnings`. Technical impossibilities are never overridable (`_commercial_combo_errors`, and `_accessory_errors`: a cassette without a decorative panel, or a cassette, ducted, ceiling or Toshiba RAV floor-standing unit without a controller — wall, console and other floor-standing units come with a remote; `quote` then says override_reason won't bypass it): more commercial (RAV/CAC) indoor units than outdoor units without a Twin/Triple kit or refnet, or indoor capacity far above the outdoor unit's. When the model doesn't pass `budget_eur`, `quote` takes the budget from the customer's own words (`_customer_budget`). A salon or medical practice with a commercial wall unit is an (overridable) error: it blows at clients, the rule prescribes an under-ceiling unit (or a cassette under a suspended ceiling). Warnings also cover keyword-inferred commercial places (offices up to 25 m² exempt), undersizing against m², a Wi-Fi wish on a set without Wi-Fi as standard (with the cheapest same-size set that has it, from the series' `key_features`), and a "cheap" wish when a cheaper suitable set exists (`_cheapest_set`: enough kW for the m², Wi-Fi and a single named brand respected). Wishes are matched on diacritic-folded text and not when negated (`_wished`: "neriešim wifi", "nechcem najlacnejší"; "základný rad" / "obyčajná" / "pomer cena/výkon" count as cheap). One set bigger than the room needs is an (overridable) error when the same series has a smaller size that still covers the m² (above the undersizing limit) — as a warning the model ignored it. The same goes for a multi-split wall unit bigger than the largest room the customer named needs, and a Wi-Fi wish on a multi-split wall unit without Wi-Fi as standard is a warning naming the cheapest same-size one with it (`_unit_has_wifi`: the multi-split price lists have no `key_features`, the same series' single-split sets do; `_wall_multi_units`). "20mm2" counts as 20 m² (`_CUSTOMER_M2_RE`). N identical multi-split systems are an (overridable) error when one outdoor unit of the price list takes every indoor unit (`_multi_outdoors`, check_compatibility's limits: four rooms got 2× AJ050 although AJ080 takes four), and an incompatible multi-split names the outdoor units that would take them. One outdoor unit bigger than the smallest one with at least the indoor units' total cooling is an (overridable) error too. Oversizing errors give way to `override_reason` only when the customer asked for more power or a reserve, typed a kW figure or a code (`_BIGGER_WISH_RE`) — the model used to override them with "the customer wants this series". The indoor unit type: a wall unit is the standard, so a residential console, cassette or ducted unit (`_NON_WALL_PATH_RE` on the section path) is an (overridable) error unless the customer asked for that type (`_INDOOR_TYPE_WISH_RE`) or typed its code; discovery asks for the type with wall-mounted as the recommendation. "The best AC" (`_BEST_WISH_RE`: "najlepšiu", "prémiovú", "špičkovú", not "najlepší pomer cena/výkon") means the best filtration and the most features (the owner, 2026-10-21): the server context asks for tier-1 series only, one per brand, with no cheaper second option, `quote` warns about a tier-2+ set or multi-split wall unit, and `cheaper_alternative` stays off. A quality comparison ("kvalitnejšia") also puts the ranking in the server context. Allergy, dust, air quality or a filter wish ("kvalitný filter", "filtrácia") in the customer's words (`_ALLERGY_RE`) puts the filtration ranking (`filtration_policy.json`, tiers 1–4, equal within a tier) into the server context and makes `quote` warn about a tier-2+ set, naming the tier-1 series of the same size (a single named brand respected). `_check_filtration_policy()` stops startup when a residential wall series is unranked or a ranked one no longer exists. Two to five single-split sets in one quote (no commercial place, no multi outdoor) get a warning to price a multi-split too. A Toshiba multi-split outdoor unit with no more indoor units than outdoor units gets a warning that it only cools (the price list's `combinations_table`). `_canonical_code` also accepts a Toshiba code that differs only in its `-E` / `-E1` / `-E2` revision when a single revision exists (the 2.5 kW HAORI indoor unit is `-E2`, the other sizes `-E1`).

The PM brief also states facts from the customer's own words when the model didn't store them: the budget (`_customer_budget`, with "vrátane montáže" / "s DPH" scope), the m² and the conversation language (a Czech customer is "cs (bot odpovedal po slovensky)"). The `capture_lead` hallucination guard checks only code-like tokens (`_HANDOFF_CODE_RE`, with a stop-list for "DPH 23", "WIFI 09", "cca 17"), so descriptions next to codes in `interested_in` are fine.

`discounts.json` holds the whole pricing policy: `category_discount_pct` (one percentage per category, the same for both brands — every category 10 % and no B2B extra since 2026-10-20, the owner's decision, so every chat price is exactly 10 % off), `customer_segment_modifiers`, `active_promotions` and `recycling_fee_eur_per_unit`. It's loaded once at import; `_check_pricing_policy()` raises `SystemExit` if a category is missing, a percentage is outside 0–100 or a promo names an unknown category. Segments with `verification_required` (dealer, installer, wholesale) are refused by `quote` and left out of its schema enum (`CHAT_SEGMENTS`) — a salesperson verifies them.

Resolving a code to a price, without touching the data files:
- **Sets:** `_SETS` maps each set's code pair (from `set` strings or `indoor`+`outdoor`) to its record; requested pairs get `set_price_EUR`. A lone code that belongs to a set is refused unless a multi-split outdoor is in the request and the code is in that outdoor's own price list (a Samsung multi outdoor once let a lone Toshiba single-split outdoor through, sold as a "set"). Units of two brands in one call are refused too: one quote is one system of one brand, so each variant gets its own quote and its own total.
- **Role-aware price:** `_unit_price()` picks `indoor_price_EUR` / `outdoor_price_EUR` by the code's role. The index's own `catalog_price_eur` takes the first price key found, which gives CAC outdoor codes their indoor unit's price — don't use it for quoting.
- **Multi-split:** when a request contains an outdoor with `max_indoor_units`, indoor units are priced from the same price list as that outdoor and `check_compatibility` runs automatically (an incompatible combination is an error). A successful multi-split quote also counts as a compat check for the multi-split validator guard. One multi-split system per call, or N identical ones (outdoor qty N, every indoor count divisible by N; one system is checked); two different multi outdoors in one call are an error.
- **Ambiguity:** a code with more than one distinct price is an error listing the options — never a silent pick.
- **Discount categories:** `_discount_category()` is brand-neutral. `code`-role records (non-units) are `panels` if their section path contains "panel", `controls` if it matches `_CONTROLS_RE` (controllers, remotes, sensors, Wi-Fi, BMS, central), else `accessories`. Units are categorized by the folder they sit in: `single_split_sets` (priced as a set) / `single_split_units`, `multi_split_outdoor|indoor`, `commercial_outdoor|indoor` (`model` rows are outdoor units). All 742 priced records map; the categories are listed in `DISCOUNT_CATEGORIES`.
- **Availability:** `_availability()` from `stock_policy.json`: a code in `non_stock_codes` or matching `non_stock_code_patterns` makes the line non-stock, else the brand default (Toshiba stock, Samsung "PM confirms"). The non-stock rule file refers to the field.
- **RAV set prices** (`set_prices` sections in `rav_indoor.json`, keyed `models`) aren't indexed; `quote` prices RAV units one by one. The catalog sets include the RBC-ASCU32Y-E controller (and the panel for cassettes), so the bot must add those codes — the kazety rule says so.

**Price provenance check** (`_untrusted_amounts` in the validator): **every** euro amount in a reply — `1 290,50 €`, `€ 1 290`, `€3,500`, and the lower bound of `800–1 200 €` — must be within ±1 € of a euro-valued field (`_euro_fields()`: numbers under keys containing `eur`) of a `quote` result in `S().quotes`, of a euro amount the customer typed (`_customer_amounts()`: a whitelist — a number next to a currency, or after a budget/price word and not followed by a unit, so `32 A`, `20 m²` or an IČO never count), or of a code-verified difference / sum of same-basis quote totals (or of a total and a customer amount). A three-quote combination (a + b − c, d03) counts only as a difference: written as a price ("Cena: …") it's an unquoted variant (`_combination_prices`). There is no minimum amount and no installation exemption; an amount written with cents must match to the cent. On top, an amount must belong to the product it is written next to (`_misattributed_amounts`: per paragraph / table row, the named series — `_SERIES_PATTERNS` — codes or brand must match the quote the amount comes from) and its DPH label must match the field it comes from (`_vat_mislabeled_amounts`). Prices from `search_knowledge` / `lookup_product` don't count (catalog, pre-discount), nor does the conversation summary. Any `~` / `cca` / `okolo` / `približne` before an amount or a range is flagged too. Both are HARD violations for the output gate. There is no calculator tool — it was removed so the model has no way to do price math.

Samuel Malíšek Klimabot does **not** offer the hidden 2% negotiation buffer — the `negotiation_buffer` block was removed from `discounts.json`. If a customer haggles beyond the computed discount, the bot politely declines and offers a cheaper model or human handoff.

`category_path` always starts with the capitalized brand from the directory name (`knowledge/samsung` → `Samsung`); `_brand_from_dir()` and `_record_product()` keep these aligned. `category_path` here is the price-list section path, not the discount category.

### Product index

`_build_product_index()` walks every brand JSON at startup (`brand_dir.rglob('*.json')`, skipping `*glossary*.json`) and registers every model code under fields `set/model/indoor/outdoor/code` (`code` covers panels and accessories). Set strings like `"AR70H09CAAWNEU + AR70H09CAAWXEU"` are split on space/`+`/comma — **never on `/`** because Samsung suffixes like `/EU` are part of the code. `lookup_product` falls back to stripping `/EU`-style region suffixes, then a real code inside other words ("Toshiba RAS-2M10G3AVG-E"), then a unit type (`_type_units`, `_UNIT_TYPES`: "Toshiba kazetová 2,5 kW" → the matching residential single-split sets, residential multi-split indoor units — the residential cassettes are only there: Toshiba 1-way FLAT and 60x60, Samsung WindFree Mini 4-Way and 1-Way — and commercial RAV / CAC units, each with `outdoor_options` — the three smallest big-enough multi-split outdoors of the brand, or the same-size commercial outdoors — plus `panel_options` read from the series' `required_panel(s)` (`_series_panels`) and `controller_options` (`_CONTROLLER_OPTIONS`); "multi-split" / "FJM" with no other type → the residential multi-split wall units, with `wifi_standard`, `outdoor_by_rooms` (the smallest outdoor unit for 2–5 such units) and filtered by a named series — "Samsung Comfort" names Comfort S2 — the kW being one indoor unit's; a size the type doesn't have returns the next size up of each brand and kind (every size when there's none), and "RAV / CAC / komerčná" or "RAS / FJM / multi / domácnosť" narrows the kind), then a series name (`_series_sets`, `_SERIES_PATTERNS`: "HAORI 2,5 kW" → the exact set codes of that series, filtered only by a size in kW — "DAISEIKAI 10" is a name — with each series' listed `series_features`, so the model states features as the catalog does), then a fuzzy prefix match. The prompt sends the model there for set codes instead of `search_knowledge`.

`check_compatibility` validates two FJM/multi-split rules: indoor count ≤ `max_indoor_units` and combined cooling kW ≤ 176% of outdoor kW (Samsung spec).

### Safety

- **Boundaries (the owner's guidelines, `knowledge/rules/feedback_mimo_temy_a_bezpecnost.md`):** off-topic questions (health and medicines, law, politics, homework, recipes, personal questions) get one polite sentence and a return to air conditioning; no medical advice; the bot says it's an AI assistant and keeps its instructions and model to itself; no personal data about staff or other customers. These live in the prompt ("Bezpečnosť a hranice" + the checklist); code backs three of them: a claim to be human is a HARD violation (`ai-identita`); when the customer's message reports danger (`_DANGER_RE`: smoke, sparks, a burning or gas smell, a shock — narrow on purpose, "horí mi to" is an idiom) and the final reply doesn't mention 112, code opens it with `_SAFETY_FIRST` (breaker, don't touch, 112; `safety_notice_added`); health terms (`_HEALTH_RE`: a diagnosis, not product wording like "antialergický filter") are replaced by `HEALTH_REDACTED` in `update_customer_state`, the `capture_lead` summary, the auto-capture's quotes of the customer and `request_human_handoff` (`health_data_redacted`) — health data is a special GDPR category the consent doesn't cover. The conversation log keeps the customer's own words.
- **Industrial spaces** (the owner's decision, 2026-10-18): a hall, production, a factory in the customer's words (`_INDUSTRIAL_RE`, triggers in `sizing_policy.json` `industrial`; not plain "sklad", not "tovar") make `_industrial_case()` true. The server context tells the model not to design, search or price, but to give the company contact or offer — as a condition, since the premature-promise check applies — that the PM calls back once the customer leaves a name and phone or e-mail; `quote` refuses (`quote_refused_industrial`), code appends `_industrial_contact_text` when the reply lacks the contact (`company_contact_appended` reason `industrial`), and asking for the contact before a price isn't `kontakt-pred-ponukou` there. Rule: `knowledge/rules/feedback_priemyselne_priestory.md`.
- **Self-installation** (live demo 2026-10-21): a customer installing a unit they already have, or asking how to install one (`_OWN_INSTALL_RE`: "montujem", "ako ju mám nainštalovať", "ktorým smerom otočiť"), gets a server-context note — no advice of any kind (placement, refrigerant, warranty, the manual) and no m² / rooms / features discovery, only a pointer to the project manager (the one from the site visit, else the company contact); the owner's decision, 2026-10-21. `_offer_due` stays off for such a message. Rule: `knowledge/rules/feedback_vlastna_montaz.md`. The permit check also catches "správa domu".
- `JAILBREAK_PATTERNS` regex over each user input; logs `jailbreak_suspected` and prints a notice but does not block — the model is expected to refuse via the system prompt's "Bezpečnosť a hranice" section.
- Spend: see "Spend caps" under Agentic loop and the demo limits under Web debugger. Per conversation, `capture_lead` succeeds at most 3 times (corrections included), `request_human_handoff` runs at most twice and the auto-capture tries at most twice; `quote` takes at most 20 items and `compare_products` at most 6 codes.
- `COMPANY_EMAIL` (default `info@klimabot.example`) and `COMPANY_PHONE` (empty by default — no number is invented) come from the environment; `_contact_offer()` builds "napíšte nám na … alebo zavolajte na …".
- Out-of-scope topics (returns, complaints, post-install support, legal) route to `request_human_handoff` → `handoff_queue.jsonl` (with `purpose: support`, no personal data) and the customer gets the company contact. Sales intent routes to `capture_lead` → `leads.jsonl` + `handoff_records/*.md`. Both record types embed `customer_state` (without personal data before consent, for the handoff queue) and the current log filename for traceability. For a sales handoff, `request_human_handoff` only promises a callback when a contact with sales consent exists; otherwise it tells the model to ask for the contact (code then asks the consent question) or give the company contact.
- Auto-capture safety net (`_should_auto_capture`): when sales consent is recorded and a contact is known but no lead has been written (`handoff_path` is empty), code calls `capture_lead` with a programmatic summary at the end of the turn — also when the turn ends in a landing or an API error. Never on readiness words in the customer's text.
- Installation permits and consents (owners' association, building manager) are the PM's topic at the site visit: the bot never asks where the outdoor unit goes or raises permits. The validator flags placement enumerations and any mention of the topic (`_PERMIT_TOPIC_RE`); the rule is `knowledge/rules/feedback_umiestnenie_outdoor.md`.
- Refrigerant sales (R32, R410A, R134a, R407C in `knowledge/montaz/cennik.json`) require **F-plyn certification** under EU 517/2014. The cennik metadata flags this; the bot must NOT sell refrigerant directly to end users — it refers them to a certified installer or the Samuel Malíšek Klimabot office.

### Logging & cost

Every meaningful event (`session_start`, `session_reset`, `user_input`, `assistant_reply`, `search_knowledge`, `llm_turn`, `tool_call`, `quote`, `quote_fit_refused`, `quote_fit_overridden`, `customer_state_update`, `consent_write_ignored`, `lead_info_auto_extracted`, `consent_question_appended`, `consent_question_shown`, `consent_recorded`, `consent_refused`, `consent_withdrawal_requested`, `session_state_write_failed`, `summarized`, `jailbreak_suspected`, `bot_reply_sanitized`, `bot_reply_regen_triggered`, `bot_reply_sentences_dropped`, `bot_reply_violations` (soft), `bot_reply_narration_dropped`, `max_tokens_truncated`, `capture_lead_blocked_gdpr`, `capture_lead_blocked_hallucinated`, `lead_captured`, `auto_lead_capture_triggered`, `handoff_regenerated`, `handoff_requested`, `lead_mail_queued`, `lead_mail_sent`, `lead_mail_failed`, `lead_mail_skipped` (`reason`: daily_cap, network_daily_cap, duplicate_contact, consent_withdrawal_requested), `api_error`, `api_retry`, `api_spend_limit`, `limit_hit`, `turn_end`, `customer_state_too_big`, `capture_lead_blocked_limit`, `capture_lead_blocked_not_cheapest`, `final_call_tool_use_dropped`, `tool_text_hidden`, `company_contact_appended`, `safety_notice_added`, `handoff_refreshed`, `reply_feedback`, `health_data_redacted`, `session_end`) is appended as JSONL to `logs/<timestamp>.jsonl`, with personal data masked before consent (see Agentic loop). The pair `user_input` + `assistant_reply` produces a complete conversation transcript — essential for GDPR/ÚOOÚ audit (you can prove what the bot asked, what the customer answered, and whether explicit consent was given).

Every API call is logged as `llm_turn`, including the side calls — `stop_reason` is `hyde`, `summary`, `regen_discarded` or `max_tokens_retry` for those (`_record_usage()`), and they are charged to the session too (`input_tokens`, and `cost_usd`, logged as `usd`), so the conversation cap and the web demo's daily budget see all spend. `cost_report.py` aggregates these with the prices in `model_prices.json`, the same file the caps use; its safety section counts `limit_hit` events by limit. It also runs a **GDPR compliance audit**, independent of the bot's own `consent_recorded` event and using the same `consent_phrases.json`: a lead is `ok` only if an `assistant_reply` showed the canonical **sales** question, the very next `user_input` said an explicit yes (and no refusal), and only then `lead_captured`. A lead before the yes, after a paraphrased question, or with support-only consent is a `violation`; sessions with `lead_captured` but zero `assistant_reply` events (pre-2026-05-13 logs) are `unverifiable` (audit gap, not a violation). Over the first eval run it flags exactly the four leads the reviewers found (c01, c12, c14, c18). Other sections: conversion funnel, lead quality, daily rollup, tool call distribution, safety/errors, reply feedback (thumbs in the web chat, with the replies rated down), averages. The web app shows the same report at `/admin`. Run with `-o` / `--output PATH` to also save to `reports/cost_report_<YYYY-MM-DD>.txt` (default path) or to a custom path; `reports/` is gitignored due to PII.

### Conversation summarization

`maybe_summarize()` triggers when the conversation has more than `HISTORY_MAX_USER_TURNS` (15) customer messages — tool rounds don't count, the history is cached anyway — or is longer than `HISTORY_MAX_CHARS` (200 000 characters): summarize the head with Haiku, keep last 14. The cut point is advanced forward to the next `user` message so `tool_use`/`tool_result` pairs are never split across the boundary — preserve this invariant when editing.

### HyDE expansion

`expand_query()` calls Haiku once per query to write a hypothetical answer, concatenated with the raw query before retrieval. Skipped when the query is already specific (>6 words OR matches `_MODEL_CODE_RE`); deduped via `_HYDE_CACHE` (process-wide, the 2 000 most recently used queries). Adds ~1s and a few hundred tokens per non-trivial turn. Finished searches are cached process-wide too (`_SEARCH_CACHE`, the 500 most recently used `(query, k)` pairs, logged with `cached: true`), but only when the HyDE expansion ran normally — one skipped for a conversation's budget or an API error isn't shared.

### Web app (`web/`)

A Flask + SSE app that wraps `bot.py` for interactive debugging in a browser. Layout:

- **Header**: brand + the conversation's API cost ("Rozhovor: 0,034 $", `session_usd` from `turn_complete` / `done`; debugging only) + the "Ladenie" switch + "Nová konverzácia" (confirmed in a `<dialog>`; `/api/reset` replaces the visitor's `Session` with a fresh one, new log file). In demo mode a strip below it warns visitors to use made-up personal details.
- **Customer view**: the header's "Ladenie" switch shows tool chips, server notices and the left sidebar; without it the visitor sees only the chat and the PM record. It is off by default when `/api/config` says `demo`, on otherwise; `?debug=1` / `?debug=0` override, and the visitor's choice is kept in `localStorage`.
- **Left panel "Poznámky bota"** (debugging only): live `CUSTOMER_STATE` rendered as a definition list. Fields are sorted by importance (lead_* → consent_* → place_* → segment → model_* → predpriprava_* → outdoor placement → features → other).
- **Center**: chat in a centred column. An empty conversation shows a welcome card with example questions (`.suggestion`, one click sends). Bot replies are rendered as sanitized Markdown (bold, lists, tables); user messages as plain text. While the server prepares and checks a reply, a typing row shows what is happening in customer words (`TOOL_LABELS`: "Počítam cenu…" for `quote`). Tool calls are small indigo chips (debugging only). The composer counts characters near `max_message_chars` and shows the messages left near `max_turns` (both from `/api/config`); the visitor can type while the bot answers. New content is followed only when the visitor is at the bottom, otherwise a "Nové správy" button appears. Under a reply that states a quote's total the chat shows a price card (`quote` event; the discount as a percentage — one rate, or the overall rate plus each line's rate when categories differ — and a "Toto chcem" / "I want this" button that sends "Chcem túto ponuku: <lines> — <total> s DPH." as the customer's message); under the consent question two buttons (`quick_replies`); under every bot reply 👍 / 👎, sent to `POST /api/feedback` and logged as `reply_feedback` (rating, reply number, a 300-character excerpt; 30 per network per minute).
- **Right panel "Zápis pre projektového manažéra"**: an empty state until `capture_lead` fires, then the handoff Markdown as a document card with a "Pripravený" badge and Copy / Download (.md) buttons.
- **`/admin`**: today's demo spend, open conversations, leads, GDPR violations, reply feedback and the full `cost_report.py` report over the logs in the data dir (conversations without a customer message are left out). Off (404) unless `KLIMABOT_ADMIN_TOKEN` is set; HTTP Basic auth with any user name and that token as the password (compared in constant time, 20 tries per network per minute); `Cache-Control: no-store` like `/api/history`, both carry personal data.
- **Narrow screens (< 1024 px)**: one panel at a time, switched by tabs under the header (Rozhovor / Zápis pre PM / Poznámky); a new PM record puts a dot on its tab and shows a toast. Light and dark themes follow the OS (`data-theme` on `<html>` overrides).

`bot.py` exposes a `run_user_turn_streaming(user_input)` generator that yields `(event_name, data)` tuples — used by both the CLI REPL (`_run_cli_repl`, kept under `if __name__ == "__main__":`) and Flask SSE. Event types:

| Event | Payload | UI handling |
|---|---|---|
| `token` | `{text}` | the checked text of one LLM response → bot bubble |
| `notice` | `{text}` | yellow center-aligned chip |
| `tool_call` | `{name, input}` | indigo chip between bubbles |
| `tool_result` | `{name, is_error, output_preview}` | mark previous tool chip red if error |
| `state` | full `CUSTOMER_STATE` dict | re-render left sidebar |
| `handoff` | `{markdown, path}` | render the PM record panel (sanitized Markdown) |
| `turn_complete` | `{input/output_tokens, cache_*, stop_reason, session_total, session_usd}` | next text starts a new bubble |
| `error` | `{message}` | red error chip |
| `quote` | `_quote_card()`: lines, totals, fee, budget — formatted by code | price card under the reply; sent at the end of the turn for each quote of the turn whose total the shown reply states (`_quotes_in_reply`) |
| `quick_replies` | `{kind: "consent", options: [{text, kind}]}` | buttons under the consent question; removed by the next message |
| `done` | `{session_tokens, session_usd, messages}` | end of one user turn |

A new tab calls `POST /api/session` and sends the returned id as the `X-Session-Id` header (a header, not a cookie, so it also works inside iframes such as a Hugging Face Space); the id is kept in `sessionStorage`, so a reload of the same tab resumes the conversation: the page fetches `GET /api/history` — the events this tab was shown (`Visitor.transcript`, `TRANSCRIPT_EVENTS`, rolled back with a cut-off turn, at most 1 500) — and replays them through the same handlers. `web.py` keeps a `Visitor` per id in memory (max 300). A conversation is finished — `bot.end_session()`, which also mails its lead — when its tab closes (`navigator.sendBeacon` on `pagehide` → `POST /api/end`, the id in the body because a beacon can't set headers; skipped when the page goes into the back/forward cache), but only after `END_GRACE_SECONDS` (20) in which any request from the same id (the reloaded page) cancels it; also after `KLIMABOT_IDLE_MINUTES` (30) without a message (a sweeper thread checks every 5 s; a reply still being prepared is never ended), or when the app shuts down (an `atexit` hook; SIGTERM is turned into a normal exit). When the registry is full, only visitors quiet for 10 min may be dropped, otherwise a new session gets 503; `bot.end_session()` always runs outside the registry lock. `web.py` holds a per-visitor lock so one turn runs at a time, and rolls back the conversation if a stream is cut off mid-turn (a dangling `tool_use` would break the next API call). The lock is released via `Response.call_on_close`, which runs even if the client disconnects before the stream starts.

Public demo: the limits are **on by default** (`KLIMABOT_DEMO=0` turns them off for local debugging) — messages per session (`KLIMABOT_MAX_TURNS`, 25), message length (800), request body 16 KB, new sessions per network per hour (20, a Reset counts too), messages per network per minute (8), 2 turns running per network, 6 turns running in total (`KLIMABOT_MAX_CONCURRENT_TURNS`), and two daily USD budgets (UTC day): per network (`KLIMABOT_IP_DAILY_USD`, $2) and across all visitors (`KLIMABOT_DAILY_USD_BUDGET`, $5). A network is an IPv4 address or an IPv6 /64. Before a turn `web.py` reserves the most it may cost (`TURN_USD_CAP`, or what is left of the conversation's budget) and settles the real cost (`sess.cost_usd` delta) when the stream closes; the totals are saved to `.demo_spend.json` (networks as salted hashes, the salt changes daily) so a restart doesn't reset them. Refusals are logged as `limit <kind> net=<hash>`; error texts are generic and give `COMPANY_CONTACT`. `KLIMABOT_REPO_URL` adds a source link to the banner; `HOST`/`PORT` set the bind address. Behind a reverse proxy set `KLIMABOT_TRUSTED_PROXIES` to the number of proxies (1 on a Hugging Face Space): only then is `X-Forwarded-For` trusted, via Werkzeug's `ProxyFix`, which reads the hop those proxies appended — the rest of the header is client-controlled and would let anyone dodge the per-IP limits. State is in-process, so run a single worker process. These limits are a first line of defense — the Anthropic Console spend limit on the demo's workspace is the real backstop (and `bot.py`'s breaker turns hitting it into a polite offline reply). `web.py` calls `os.chdir(PARENT_DIR)` before `import bot` so relative paths (`knowledge/`, `config/`, `data/`) resolve from the project root regardless of where `web.py` is launched from.

The HTML/CSS/JS lives entirely in `web/static/index.html` (single file, ~1 100 lines, vanilla JS, design tokens as CSS custom properties). No build step. marked and DOMPurify are pinned local copies in `web/static/vendor/` (version in the file name, SHA-256 checked against jsDelivr when added); nothing is loaded from a CDN. `web.py` sends `X-Content-Type-Options`, `Referrer-Policy` and, on the page, a Content-Security-Policy that allows only the app's own origin (`'unsafe-inline'` because the UI is one file; framing allowed for a Hugging Face Space). To update a library: download the new version into `vendor/`, check its hash, change the `<script src>` and run the tests (`WebTests` checks that every script on the page is local and served).

## Conventions

- Slovak is the primary content language. Print messages, tool descriptions visible to the model, and system-prompt instructions stay in Slovak; Python identifiers and code comments stay in English.
- `claude-haiku-4-5-20251001` is used everywhere (main turn, HyDE, summarization). Don't introduce a different model without a reason.
- Files written by the bot at runtime, all under `KLIMABOT_DATA_DIR` (`DATA_DIR`: `data/` by default, `/data` in Docker; `cost_report.py` reads the same setting): `logs/`, `leads.jsonl`, `handoff_queue.jsonl`, `handoff_records/`, `sessions/`, `.kb_vecs.npy`, `.kb_hash.txt`, `.spend_breaker.json`, `.demo_spend.json`, `.lead_mail_sent.json`. All are gitignored (PII concerns for `leads.jsonl`, `handoff_records/`, `sessions/`).
- Web debugger dependency: `flask` (3.1+). Installed by `./setup_project.sh`. No other web-side dependencies — UI uses vanilla JS + local copies of marked and DOMPurify (bot replies and the handoff Markdown contain visitor-typed text, so they're sanitized before rendering).
- `knowledge/samsung/` and `knowledge/toshiba/` are real data transcribed from the manufacturers' public price lists (attributed in each file's metadata and the index headers; see README → Data). `knowledge/montaz/` is a mock sample and `discounts.json` is illustrative (a uniform 10 %, set by the owner on 2026-10-20). Keep the source attribution when updating the data.
- Rule files in `knowledge/rules/` contain no concrete euro amounts — the model could repeat them, and every amount must come from `quote`. Examples use output field names (`total_eur`, `total_with_DPH_23pct_eur`) and never an installation price. Likewise, sizing thresholds live only in `sizing_policy.json`, the filtration order only in `filtration_policy.json`, stock status only in `stock_policy.json` and the consent wording only in `consent_phrases.json`; rules refer to them instead of restating them. What the bot may claim about health, warranty and stock is in `knowledge/rules/feedback_schvalene_tvrdenia.md`.
- `consent_phrases.json` is marked as a draft: the wording and the legal basis (consent vs. Art. 6(1)(b)) still need the DPO's approval. Changing a question changes the audit too — older logs with the old wording no longer pass.
