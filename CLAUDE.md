# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the **Samuel Malíšek Klimabot** — a chatbot tailored for Samuel Malíšek Klimabot. Samuel Malíšek Klimabot sells only Samsung and Toshiba (RAS residential, RAV commercial). No other brands.

## Running the bot

```bash
bash setup_project.sh          # creates .venv and installs deps from pyproject.toml (--recreate starts fresh)
source .venv/bin/activate      # Git Bash on Windows: source .venv/Scripts/activate
python main.py                 # web app on http://127.0.0.1:5000 (runs web/web.py)
python bot.py                  # interactive CLI (type 'bye' to quit)
python cost_report.py          # token/cost summary across data/logs/*.jsonl
python -m pytest               # browser tests (tests/e2e), after pip install ".[e2e]" && python -m playwright install chromium
make build / make web / make down   # the web app in Docker on http://127.0.0.1:7860 (docker compose)
```

**Repository layout.** `bot.py` (the whole bot, one file on purpose), `main.py` (starts the web app) and `cost_report.py` (imported by `web/web.py` and the tests) stay in the root; the Dockerfile too, because Hugging Face Spaces build from the repo root.

```
config/      discounts.json, consent_phrases.json, sizing_policy.json, stock_policy.json, model_prices.json, filtration_policy.json
knowledge/   samsung/, toshiba/, montaz/ (price lists) and rules/ (behavior rules) — everything retrieval reads
dictionaries/  sk_SK.aff/.dic (sk-spell's Hunspell dictionary, unchanged, with its README and licence) + klimabot_sk.txt (our extra words)
web/         web.py + static/ (index.html, vendor/)
tests/       test_guards.py, test_robustness.py, e2e/ (Playwright browser tests: conftest.py, test_chat.py, test_accessibility.py, test_mobile.py)
eval/        run_eval.py, analyze.py, stability.py, judge.py, test_scenario.py, scenarios/, runs/ (gitignored)
docs/        reference moved out of this file (output_gate, server_context, fit_check, testing), conversation_policy, QA reports, screenshot
data/        runtime output, gitignored (KLIMABOT_DATA_DIR): logs/, sessions/, handoff_records/, leads, caches
```

`bot.py` finds them through `CONFIG_DIR`, `KNOWLEDGE_DIR` and `DATA_DIR`; chunk sources are stored with `/` (`knowledge/rules/…`) on every OS.

Requires `ANTHROPIC_API_KEY` in `.env` (see `.env.example`). The bot raises `SystemExit` on missing key.

**Docker** (`Dockerfile`, `docker-compose.yml`, `.dockerignore`; README → Docker): one container, one process. The image installs the CPU-only PyTorch, puts both models into `HF_HOME=/opt/hf` (then `HF_HUB_OFFLINE=1`) and builds the KB embedding cache into `/app/.kb_cache` by running `import bot` with a dummy key and a throwaway data dir, against a BuildKit cache mount (`id=klimabot-kb`) that keeps the vectors between builds, so only a change to the knowledge base re-embeds it (the fingerprint covers the final chunk texts and the model; a code-only deploy no longer takes 15–20 minutes) — so any change to `bot.py`'s import-time behavior must still work with no `.env`, no network and no mail settings (the spelling dictionary loads at import too, from `dictionaries/`, in about half a second). The commit is a build arg (`KLIMABOT_COMMIT`, declared after the KB step so it doesn't invalidate it). It runs as uid 1000 (Hugging Face Spaces), with `KLIMABOT_DATA_DIR=/data` as the volume and port 7860. `web.py` turns SIGTERM into a clean exit that ends open conversations (mailing their leads), hence `stop_grace_period: 60s`. Sessions live in memory, so a deploy (`make web` recreates the container; the old one serves while `make build` runs) ends every open conversation: check `/admin` or the newest logs for activity before restarting. The app's port is published on 127.0.0.1 only and compose sets `KLIMABOT_TRUSTED_PROXIES=1`. On a server, the `caddy` service (compose profile `https`: `COMPOSE_PROFILES=https` + `KLIMABOT_DOMAIN` in `.env`; `Caddyfile`, image pinned by digest) terminates HTTPS with Let's Encrypt and proxies to `klimabot:7860`. It has no `encode` (it would hold back the event stream), and it replaces the client's `X-Forwarded-For`, which is the one hop `web.py` trusts. That VPS + Caddy setup is the recommended public deployment (README → Docker → On a server).

First run downloads two HuggingFace models (~750 MB total): `intfloat/multilingual-e5-base` (embeddings) and `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` (reranker). The reranker is loaded lazily on the first `search_knowledge` call.

**Tests** (the full reference, with each suite's first run and what it found, is in [docs/testing.md](docs/testing.md)): `tests/test_guards.py` (stdlib `unittest`, `python -m unittest discover -s tests`, about 30 s) covers the guarantees that live in code. The model is a `FakeClient` that replays scripted responses or raises scripted SDK errors, and fails on a `tool_use` without its `tool_result`, a misplaced system message or a thinking block sent back after anything before it changed — no key or network, but importing `bot` loads the embedding model. `tests/test_robustness.py` (metamorphic, no model, about 5 s; `--report` prints a table) multiplies the phrasings code reads by meaning-preserving transforms: a new phrasing that code must read belongs in a family there. `tests/e2e/` (pytest + Playwright, Chromium, about 15 s; `python -m pytest`) runs the real web app with a scripted model, axe-core WCAG 2.2 AA scans and the phone cases (`test_mobile.py`: the on-screen keyboard played through a fake `visualViewport`, small screens, no entrance replayed after a reload): keep the page at zero violations and keep the roles and names `ChatPage` finds it by. `.github/workflows/tests.yml` runs all three on every push to main and every PR. On Windows set `PYTHONIOENCODING=utf-8` when the output is piped. **Eval** (`eval/`): scripted customer conversations through the Claude Code CLI on the subscription by default — `run_eval.py` then `analyze.py`, `stability.py` (direction metrics, a post-commit hook, `--history`), `judge.py --cli` (the AI review, which now reads full tool results, not the 300-character preview), `test_scenario.py` for one conversation; `--api` uses the paid API with a budget and needs the owner's OK. Scenario sets: `conversations.json`, `scenarios/` (boundaries, redteam, abuse, direction, qa_csat, round2_*).

## Architecture

`bot.py` is an intentionally flat ~11,600-line monolith — the whole agentic pipeline reads top-to-bottom in one file. The rough order is: config + `Session` → logging with redaction → pricing policy load + product index → fit check + pricing (`quote`) → other tool implementations (incl. session persistence + handoff Markdown renderer) → tool schemas → KB load/embed/index → retrieval pipeline → tool dispatch → conversation summarization → post-reply validator → output gate → language & consent → system blocks → turn loop + REPL. When changing behavior, locate the section by header comment; don't try to refactor into modules — the user wants it readable as one file.

### Knowledge base pipeline

Everything retrieval reads lives in `knowledge/`: two brand DBs (`samsung/`, `toshiba/`) + a brand-agnostic installation accessories cennik (`montaz/`) + one rules dir (`rules/`). **Only Samsung and Toshiba are sold** — competitor DBs were removed when this bot was tailored for Samuel Malíšek Klimabot. `knowledge/rules/` contains Slovak `feedback_*.md` behavioral rules (with `RULES_INDEX.md` as an index) and gets `+0.3` in `authority_bonus()` (it matches the `knowledge/rules/` source prefix).

Each brand directory is split into category subfolders; `montaz/` is flat (one cennik per category isn't needed for installation parts):

```
knowledge/
  samsung/
    single_split/      rac.json
    multi_split/       fjm.json
    light_commercial/  cac.json
    accessories/       accessories.json
    glossary.json      SAMSUNG_INDEX.md
  toshiba/
    single_split/      ras_single.json
    multi_split/       ras_multi.json
    light_commercial/  rav_outdoor.json, rav_indoor.json
    accessories/       ras_accessories.json, rav_accessories.json
    ras_glossary.json  rav_glossary.json
    TOSHIBA_INDEX.md   RAV_INDEX.md
  montaz/
    cennik.json        glossary.json  MONTAZ_INDEX.md
  rules/
    feedback_*.md      RULES_INDEX.md
```

`load_chunks()` recurses through `<brand_dir>.rglob('*')` and tags every chunk with a `Kategória: single-split | multi-split | light-commercial | accessories` line derived from the path. This lifts BM25 recall on category-defining queries (e.g. "potrebujem multi-split do 3 izieb") so the model is much less likely to mix single-split and multi-split candidates. `_category_from_path()` maps the path segment to the human-readable tag via `CATEGORY_FOLDERS`. `montaz/` items don't get a Kategória tag (they don't sit in a category folder) — the bot finds them via BM25 keyword match on the cennik glossary aliases (silentblok → AV kits, antivibračná konzola → DXL series, etc.). Glossaries live at the brand-dir root and are discovered by `_build_alias_map()` via `rglob('*glossary*.json')`.

The montáž cennik is **not** subject to `discounts.json` and `quote` doesn't price its items (they use `kod`/`cena_EUR`, not the indexed code fields). The bot uses it only to explain what an installation includes. **The bot never states an installation price** (the owner's decision: it depends on the specific installation) — the PM prices it after the free site visit.

Per-file chunking strategy: `chunk_json_file()` emits one chunk per top-level dict key; `.md` files split on `\n\n`. After chunking, each chunk is prefixed with the `Kategória:` line and then passes through `expand_chunk_with_aliases()`, which appends a `Synonymá: ...` line built from the brand glossaries so BM25 can match SK/CZ/EN variants of the same term.

Retrieval is hybrid: BM25 (with diacritics-folded token variants so "klimatizacia" matches "klimatizácia") + cosine over e5 embeddings, fused via reciprocal rank fusion (k=60), top-16 candidates (`RETRIEVE_CANDIDATES`; 25 until 2026-11-07 — 16 is 1.45× faster at 2 threads, hit@k 37/37 → 36/37 and MRR 0.836 → 0.827 on the golden set, weak-match flags unchanged; an int8-quantized reranker was 2.5× faster but moved the score scale, 6 answerable questions under `SEARCH_MIN_SCORE`, so it would need the threshold recalibrated) → cross-encoder rerank with authority bonus → top-K. The reranker scores the pairs in batches of 8: a batch is padded to its longest pair, and on 2 threads that is about a third faster than one batch of 25, with the same ranking. K is dynamic: model code regex hit → 3, query <5 words → 8, default 5. The model can override via the tool argument (capped at 10). The tool result is plain text — each chunk under its `[source]` line, up to `CONTEXT_CHAR_BUDGET` — without the `Synonymá:` line, which only serves BM25 (it was 17 % of an average result, and JSON around the JSON chunks escaped every quote). When the best raw reranker score is below `SEARCH_MIN_SCORE` (-0.5) nothing in the knowledge base answers the query: the results still go out, but under `_WEAK_MATCH_NOTE` (state only what they say, nothing from general knowledge, the PM checks the rest, codes via `lookup_product`) — a preventive counterpart of `funkcia-bez-podkladu`. The cut is low because this cross-encoder scores Slovak rule prose low (a correct rule hit can sit at -0.1); it catches topics wholly absent, not a missing feature of a series that exists. Every `search_knowledge` event logs `best_score` and `weak` for recalibration. `tests/retrieval_golden.json` (37 labelled questions in the model's search style, with the files that answer them, plus out-of-KB questions) runs through the real retrieval in `RetrievalTests`: hit@k, MRR and the weak-match flags have floors, so a knowledge-base edit that hurts retrieval fails the tests.

Embeddings cache to `.kb_vecs.npy` with a sha256 fingerprint in `.kb_hash.txt` (in `KLIMABOT_KB_CACHE_DIR`, default the data dir; a failed write is only printed, so a read-only cache in the image can't stop the bot) that **includes `EMBED_MODEL_NAME`** — swapping the embedding model auto-invalidates the cache. Don't add a manual cache-clear step.

e5 requires asymmetric prefixes: `encode_passages()` prepends `passage: `, `encode_query()` prepends `query: `. Don't drop these — recall collapses without them.

### Agentic loop

The system prompt forbids the model from answering product/price/feature questions without first calling `search_knowledge`, and forbids manual price math — `quote` is the only source of any euro amount (see Pricing rules). There is no always-on KONTEXT block; retrieval is fully tool-driven.

Tool dispatch is all in `dispatch_tool()` returning `(content_str, is_error)`. `run_user_turn_streaming()` drives a tool loop: call the model (`_call_model()`, **not streamed**, `max_tokens` `TURN_MAX_TOKENS`, 4096, because thinking counts against it; the pinned SDK 1.x has no sampling parameters — `temperature` / `top_p` / `top_k` are gone from `create()`, and `FakeClient` refuses any argument the real `create()` doesn't take) → sanitize + gate the text → emit it → if `stop_reason == "tool_use"`, run every tool_use block, append a single user message containing all tool_results, loop. `is_error: True` on a `tool_result` lets the model recover instead of silently using a bad value. **Text written next to a tool call is neither shown nor stored** (the owner's decision: one bubble used to stack 3–7 drafts); the answer comes after the tool (`tool_text_hidden` is logged). Within the turn a response that carries a thinking block goes back whole, its hidden text with it (below). Exception: a complete reply (`_complete_answer`: no narration, a question or ≥ 160 characters) whose only tool is `update_customer_state` is the answer — the tool runs right away, the reply is stored without the tool call, and the turn ends without a second call. A price question the model leaves without a quote (`cena-neodpovedana`) regenerates with `tool_choice: any`, so the next attempt must call a tool. A response cut off at `max_tokens` is retried once with `TURN_RETRY_MAX_TOKENS` (8192; it may hold only thinking); if it is still cut off, its tool_use blocks are dropped — a `tool_use` without its `tool_result` would break every later API call of the session.

**Spend caps — in code, before every call.** Every call is priced from `model_prices.json` (`usage_cost()`; `_record_usage()` charges it to `S().cost_usd`), a prompt over 100 000 tokens at Haiku 5.5's 5× rate (`_long_context_factor`, `long_context_over_tokens`; the projection below too). Before a call, `budget_for_next_call()` compares that call's worst case (`projected_call_cost()`: the latest main call's context + 6k tokens — HyDE and summary calls don't move that base — all written to the cache, plus every output token) with what is left of the customer message (`TURN_USD_CAP`, $0.05) and of the conversation (`SESSION_USD_CAP`, $0.07; env `KLIMABOT_TURN_USD_CAP` / `KLIMABOT_SESSION_USD_CAP`). When only one more call fits — or the turn reaches `TURN_MAX_CALLS` (10) or `TURN_MAX_SECONDS` (180) — that call is made with `tool_choice: none`, so the customer still gets an answer (a tool_use returned anyway is dropped). When nothing fits, code writes the closing message without a model call (`_landing_text`: a recap of the last `quote`, `COMPANY_CONTACT`, "start a new conversation") and the conversation stays closed (`limit_reached`). Tools are bounded too: `RESPONSE_MAX_TOOL_CALLS` (6) per response, `TURN_MAX_TOOL_CALLS` (16) and `TURN_MAX_SEARCHES` (3) per turn (the reranker takes about 9 s per search on the demo server's 2 cores; the second search of a turn gets a nudge in its result, and only one search runs per response — searches asked for together are issued before any result is seen, so the rest get an `is_error` result, `limit_hit` `response_searches`) — over the cap the tool doesn't run, but its tool_use still gets an `is_error` tool_result telling the model to answer. Within a turn an identical `lookup_product`, `check_compatibility`, `compare_products` or successful `quote` call doesn't run again (`repeat_lookup`), nor does an identical refused `quote` (`repeat_refused_quote`; the same items with `override_reason` are another call, or the plain call that came first would block the fit check's way out), and `TURN_MAX_REFUSED_QUOTES` (5) refused quote calls, repeats included, make the next call the turn's last, without tools. A last call carries `_final_call_note()`: announce nothing, state only quoted amounts, else say it can't be priced here and give the contact. An offer move whose first call could only run without tools ends in the code-written closing (`limit`) instead of a reply that promises to try again. A regeneration is allowed only while the budget, with the rejected draft counted, leaves room for an answer after it; HyDE and summarization skip themselves when the conversation budget can't take them. At 80 % of the conversation budget the SERVER block asks the model to wrap up. The limits are per conversation and don't stop anyone from starting a new one — that is `web.py`'s job (per network and per day).

**API errors** (`_call_model()`; the SDK's own retries are off): a 429 with a short `retry-after` (≤ `API_MAX_RETRY_AFTER`, 10 s) and 5xx / 529 / connection errors are retried at most twice; anything else ends the turn with a generic message (`_ERROR_REPLY`, never the raw error) and rolls the turn back. A spend-limit error is never retried: the account's monthly cap (429 `enforced_spend_limit_reached`, paused until the 1st of next month UTC) or our own Console limit (400 "reached your specified …", retried after 30 min) opens a process-wide breaker saved to `.spend_breaker.json`. While it is open every turn gets a code-written "temporarily unavailable, write to us" reply and the API isn't called.

**The output gate: replies are checked before the customer sees them** — every response, tool-calling ones included (their tools haven't run yet, so regenerating them is safe). `sanitize_reply()` fixes mechanical issues and `_canonicalize_consent_question()` rewrites any consent question to the canonical wording. `validate_assistant_reply()` then sorts violations into three kinds. **HARD** ones sit inside one sentence (`_HARD_RULES`: an amount `quote` didn't produce or shown under the wrong product or DPH basis, an approximation before an amount, an invented model code, a permit or placement topic, a promise or recording claim before consent, a delivery date or a callback deadline, unsupported SEER / SCOP / dB figures or savings, a claim to be human, wrong energy class, filtration, colour, feature, stock or comparison claims, internal reasoning or tool names, health claims, an unverified phone number…): up to `MAX_REGENS_PER_TURN` (2) regenerations with a note per rule (`_regen_note`, never "keep the same content"), then whatever still violates is cut sentence by sentence (`_drop_hard_sentences`). **REGEN-ONLY** ones cover the whole reply (`_REGEN_ONLY_RULES`: Czech or English, a price question left without a quote, a contact request before any price, one option where two are due, a forbidden question, tykanie, a technology described with no tool result naming it, misspellings, "the cheapest" that isn't…): regenerated, never cut. Everything else is **SOFT**: fixed mechanically where safe (diacritics, the recycling-fee wording, repeats, the bot's feminine forms, Slovak number formats…), otherwise logged. A final reply that is still empty gets `_EMPTY_REPLY_FALLBACK`: the customer never gets silence. The history stores exactly the text that was shown, emitted as a single `token` event, so a rejected draft never reaches the browser — don't reintroduce token streaming without keeping that guarantee. Each rule exists because an eval run or a live conversation caught the model doing it: the full catalogue, with the reason and date of every rule, is in [docs/output_gate.md](docs/output_gate.md). Read it before changing a rule and add new rules there.

All per-conversation state lives on a `Session` object (`conversation`, `customer_state`, `input_tokens`, `handoff_path`, `compat_checked_outdoors`, `user_inputs`, `quotes`, `gdpr_question_asked`, the consent fields `consent_ask_index` / `consent_ask_purpose` / `consent` / `consent_refused`, `support_handoffs`, the spend fields `cost_usd` / `last_call_input` / `limit_reached`, the per-conversation counters `lead_calls` / `auto_capture_attempts` / `handoff_calls` / `consent_reasks`, `lead_record` / `lead_mail_queued` for the PM mail, `network` (set by the web app), its own `log_path`). `user_inputs`, `quotes` and the consent fields cover the whole session on purpose — `maybe_summarize()` shortens `conversation`, and the price check, the consent guard and the handoff must not lose anything when it does. Bot functions reach the active one via `S()`, which reads a `contextvars.ContextVar` set by `use_session()`. The CLI uses the default session created at import; the web app activates the visitor's session at the start of each request. Never reintroduce module-level conversation state — concurrent web visitors would share it. A thread that never called `use_session()` gets a `LookupError`, not someone else's session.

The customer state (`S().customer_state`, still called CUSTOMER_STATE in comments and tool descriptions) is mutated by `update_customer_state` (deep-merge: lists union, `None` removes keys; strings clipped to `STATE_MAX_STRING`, lists to `STATE_MAX_LIST`, the whole state refused over `STATE_MAX_CHARS`; writes to `consent_*` dropped) and by code for consent and the phone/e-mail safety net. **Prompt caching**: a request is tools → system → conversation → server context. `build_system_blocks()` is identical on every call (the persona prompt and the `CRITICAL_RULES_TEXT` checklist, with a cache breakpoint); `_messages_for_api()` sends the stored history the same way every call, with a second breakpoint on the last block of the final user message. **A turn's requests are append-only** (`turn_api` in `run_user_turn_streaming()`): each tool round goes back exactly as the API saw it, a thinking block unmodified with any text hidden next to the tool call, because a Haiku 5.5 thinking block is valid only while the system prompt, the tools and every message before it are unchanged. The stored history keeps none of it, so the context grows only by what the customer saw, and a regenerated draft is never sent back. Everything that changes per call — the move, the form of address, the customer state (as data, not instructions), the consent status, the per-topic notes — is `build_server_context()`: a `<server_context>` block appended to the final user message after the breakpoint and never stored. `discounts.json` is deliberately **not** in the prompt. **Conversation policy** ([docs/conversation_policy.md](docs/conversation_policy.md), diagram and table): `next_move()` decides once per customer turn where the reply heads — the first case that applies wins (`krize`, `bezpecnost`, `reklamacia`, `priemysel`, `vlastna-montaz`, `odvolany`, `zapis` / `po-zapise`, then the sale: `zisti-priestor`, `zisti-izby`, `zisti-priority`, `ponuka`, `kontakt`, `nova-ponuka`, `odpoved`, `pokracuj`) — and the move is kept for the turn in `Session.turn_move`. Code prices the offers it picked itself before the first call (`Move.prerun`): the results reach the model in the server context and the stored history as a `toolu_server_…` round, not this turn's request. The full reference — every move's triggers, every server-context note, the prerun rules and the measurements behind them — is in [docs/server_context.md](docs/server_context.md).

`update_customer_state` has an **explicit canonical field schema** (30+ fields with `enum` constraints for `place_type`, `usage`, `segment`, `predpriprava`, etc. — see the tool schema for the full list). `additionalProperties: true` is still set so the bot can add ad-hoc fields, but only canonical names render into the structured handoff Markdown sections — unknown fields are silently dropped from the PM brief. After each successful mutation, the state is **atomically persisted** to `sessions/<session-log-stem>.json` (tmp file + rename) so a crash mid-conversation doesn't lose discovery context. Personal data (`_PII_FIELDS`: `lead_name/phone/email/obec`) stays in memory only until code records consent — `_storable_state()` strips it from `sessions/` and `handoff_queue.jsonl`, and `log_event()` masks phone numbers, e-mail addresses and every known `lead_*` value in **every** event before consent. The server's own text — `COMPANY_NAME`, the company contact and the canonical consent questions — is never masked (`_PII_PROTECTED_RE`): the audit needs the question verbatim even when the customer is called Samuel. A name typed before the bot knew it is masked by `_scrub_session_log()` when the customer refuses or the session ends without consent (`end_session()`, called by the CLI, the eval harness and the web app on reset / idle eviction). `_auto_extract_lead_info()` copies a phone number or e-mail into the state, and a name only when the bot's last reply asked for it and the answer (or the words before the contact) is two or three plain words with a capital first ("Samo samo"; towns are not guessed) and logs field names, not values; the capitalised words typed next to the contact ("Dobrý deň, Jozef Mráz, 0907…"; only the last sentence before it, so "Zavolá mi niekto? Som Mária…" doesn't mask "Zavolá") go to `pii_seen` so the log masks them anyway. Names and towns of 4+ letters are masked with their Slovak case endings ("Nitra" also masks "v Nitre", `_pii_pattern`; case-sensitive, so the colour "biela" survives "Biely").

### Lead handoff workflow

When a customer picks a model and gives consent, `capture_lead(name, contact, summary, interested_in)` does two things, and the end of the conversation a third:

1. Appends a JSONL line to `leads.jsonl` (machine-readable record + customer_state snapshot).
2. Renders a **human-readable Markdown brief** to `handoff_records/<session-log-stem>_<slug-name>.md` for the project manager (one file per conversation, overwritten when the lead is corrected).
3. **E-mails the final brief to the PM when the conversation is finished** — `end_session()` → `_mail_lead_to_pm()`: one plain-text mail per conversation (the brief as the body, corrections included), to `LEAD_MAIL_TO` over SMTP (`SMTP_HOST`, `SMTP_PORT` 587 STARTTLS / 465 SSL, `SMTP_USER`, `SMTP_PASSWORD`, `LEAD_MAIL_FROM`; off unless `SMTP_HOST` and `LEAD_MAIL_TO` are set, a bad setting stops startup). Finished means the CLI's `bye`, the web Reset, the tab closing, an idle web session or the web app shutting down. One background worker sends the mails (`_MAIL_WORKER`), so a slow server holds nobody up; a dropped connection or 4xx is retried twice, anything else is logged as `lead_mail_failed` — the lead is still on disk. No mail after the customer asked to withdraw consent (`consent_withdrawal_requested`); one mail per contact per `LEAD_MAIL_DEDUPE_DAYS` (7; phones compared by their last 9 digits, hashed in `.lead_mail_sent.json`); at most `LEAD_MAIL_MAX_PER_NETWORK_DAY` (3) per network a day (`Session.network`, set by the web app) and `LEAD_MAIL_MAX_PER_DAY` (30) in total. On a public page anyone can type someone else's phone, so the web demo also sets `LEAD_MAIL_DEMO`: the subject starts with `[DEMO]` and the body with a warning that the details may be made up. Mail goes only to the configured addresses, never to one typed in the chat; the subject is one line, so chat text can't add headers. The eval harness and the tests blank `LEAD_MAIL_TO` before importing `bot`.

A `quote` made after the lead refreshes it in code at the end of the turn (`_refresh_lead_brief`: the record's quotes and state, a new leads.jsonl line, the brief rewritten with the latest variant marked "posledná ponuka zákazníkovi", a `handoff` event, `handoff_refreshed`), so a customer who switches models after consent doesn't leave the PM the old offer when the model skips `capture_lead`; "Záujem" then opens with "Posledná ponuka po zápise". A customer who goes back to an offer already quoted makes no new quote, so code reads it from the note: the series or code named, else "drahšiu" / "lacnú" (`_rechosen_quote`, not on a question), writes `model_selected`, marks that variant and opens "Záujem" with "Zákazník si po zápise vybral" (`lead_choice_changed`).

The Markdown's structured sections (Zákazník, Záujem, Priestor, Inštalačné prostredie, Predpríprava, Pre PM – cenové ponuky, Zdroj) are **auto-rendered from `CUSTOMER_STATE`** via `_render_handoff_sections()`, except the prices: "Pre PM – cenové ponuky z rozhovoru" lists every distinct `quote` result of the session (`_render_quotes()`: lines with availability, totals, recycling fee, "Montáž: určí PM", the budget status, fit warnings and the cheaper alternative), so the PM sees exactly what the customer was quoted. The brief also renders `notes`, the heat load (from the customer's own kW when the model stored none), rack count, 24/7 and redundancy; the segment is never assumed "retail" — without a stored one it is "B2B_firma (podľa zákazníka)" when the customer wrote IČO / s.r.o. / "na firmu" (the IČO is rendered too), else "neuvedené". The leads.jsonl record carries the same `quotes`. The bot's `summary` argument is therefore **prose-only**: it goes into the "Otvorené otázky pre PM a poznámky" section and is meant for sentiment notes, recommendation rationale, and unresolved questions. Missing canonical fields degrade gracefully to `"neuvedené"` — there is no hard validation, the bot doesn't re-ask if discovery was abbreviated. The brief's area is the customer's latest word (`_customer_m2()`), the model's `place_m2` only when the customer gave none. `summary` sentences claiming the offer fits the budget without `quote` support are dropped. When the customer's last message says "lacnejšiu" and two or more variants were quoted, `capture_lead` refuses a lead naming the dearer one. The auto-capture summary includes the customer's last messages, so the PM sees the request even when the model stored nothing. What the customer writes after the lead (`po-zapise`, three words or more) goes into the brief and `leads.jsonl` word for word, in code (`_note_after_lead`, `after_lead_notes`, health terms redacted, `handoff_refreshed` reason `customer_note`): "volajte po 17:00" got "zapíšem si" and was stored nowhere. The brief's phone and e-mail lines are split from `contact`. Helpers: `_state_get(state, *keys, default)` tries multiple alias keys (canonical English + Slovak fallback), `_fmt_value(v, fmt=None)` formats booleans (`Áno`/`Nie`), lists (comma-separated) and m²; `_eur()` formats euro amounts the Slovak way (`1 290,50 €`). See [knowledge/rules/feedback_handoff_zapis_z_rozhovoru.md](knowledge/rules/feedback_handoff_zapis_z_rozhovoru.md) for the bot-facing rule.

One contact is enough for a lead: once the customer gave a phone or an e-mail, the `kontakt` and `zapis` moves don't ask for the other one or the town (re-asking for the e-mail after the phone and the consent was the AI review's top flow finding in the API run of 9657449). **Consent is decided by code, never by the model** (section "Language & consent" in `bot.py`). The canonical question — sales only, Slovak and English, naming name, phone, e-mail, town and the chosen model — and the yes / no vocabulary live in `consent_phrases.json`, read by `bot.py`, `cost_report.py` and `eval/analyze.py` alike; earlier wordings (without e-mail, and the retired support question) are in `previous_questions`, which the audit still recognises. When a reply asks for contact details (`_asks_contact`: `_CONTACT_REQUEST_RE` after blanking a phone as a device — "ovládanie cez telefón", "telefónom", `_PHONE_AS_DEVICE_RE`), or contacts arrive without a consent answer, code appends the canonical question (the Slovak one; the English sentence in `consent_phrases.json` stays for the audits of older logs); a paraphrase the model writes is rewritten to it. Only the customer's **very next message** after the latest question can give consent (`_process_consent_reply`): an explicit yes (`yes_re`, minus "súhlasím s cenou"-style phrases in `yes_not_consent_re`) records `S().consent` with purpose, timestamp and the customer's words; "OK / beriem / môžete" don't count, and neither does a "súhlasím" typed before the question. An explicit refusal (`no_re`, incl. "kontakt vám nedám") counts at any time and wins over a yes in the same message; disagreeing with the price, the offer or a model (`no_not_refusal_re`: "nesúhlasím s cenou", "nesúhlasil som s cenou", "to nesúhlasí") is not a refusal, and neither is a "Nie" right after the question that goes on to dispute the offer — an amount, "beriem", "pomýlili ste sa" (`no_in_window_re`; QA 2026-11-03: "nie, beriem seiyu ale za cenu classic" scrubbed the log and the customer was told they didn't want their data stored) — in `bot.py` and in both audits. When contacts are known and the customer answered the question with something other than yes / no ("S tou cenou súhlasím", a stock question), code asks again — at most twice per conversation (`consent_reasks`) — and the server context tells the model what to say meanwhile (thank, explain the explicit yes is needed, promise nothing). A paraphrase of the question written as a statement is removed. After a refusal or "ozvem sa sám" code adds the company contact if it wasn't shown recently. A refusal can be taken back: an explicit agreement after it (`reconsider_re` — "súhlasím", "zmeň súhlas", not a bare "áno" or "súhlasím s cenou") records nothing, and code answers without a model call with the canonical question and its buttons (`_reconsider_text`, consent event `reconsidered`, event `assistant_reply` kind `consent_reask`), so the customer's next yes answers a question like any other and the audit passes; at most twice per conversation (`consent_reasks`). The customer of 2026-11-02 agreed three times and was told to send an e-mail. In the web chat the question comes with two buttons (`CONSENT_QUICK_REPLIES`, the `quick_replies` event): they send the explicit words "Áno, súhlasím" / "Nie, nesúhlasím" ("Yes, I agree" / "No, I don't agree") as the customer's message, so consent is still decided by code from that message and the audit reads it from the log as before (a test checks that the bot and both audits read every button the same way). A withdrawal of consent or an erasure request (`withdrawal_re`: "odvolávam súhlas", "vymažte moje údaje", "nevolajte mi") is not in `no_re`, the audits' refusal of the question. Before consent it counts as a refusal; after it `_record_withdrawal()` sets `consent_withdrawal_requested`, queues a `purpose: gdpr` line in `handoff_queue.jsonl`, marks the lead and rewrites the brief ("NEKONTAKTOVAŤ"), which also stops the PM mail, `capture_lead` and the auto-capture, and code answers with `_withdrawal_text()` without a model call. It says the data is being handled, never that it is gone. The evidence quoted in the brief passes `_redact_health`. While it stands the move is `odvolany` and a promise of contact is `slub-bez-suhlasu` as before consent. Taking it back works like taking back a refusal (`_WITHDRAWAL_UNDONE_RE`: "nerušte to", "nech sa mi ozvú", or `reconsider_re`): the words alone record nothing (`withdrawal_take_back_asked`), code answers with the canonical question and buttons, at most twice per conversation (`consent_reasks`), and only an explicit yes to it clears the flag (`_record_regrant`, `consent_regranted`): fresh consent, the banner off the brief, a `purpose: gdpr` line telling the operator. A withdrawal and a take-back in one message stay a withdrawal. `capture_lead` refuses (tool error, the model recovers) unless (a) consent with purpose `sales` is recorded and (b) every model code in `summary` / `interested_in` appears in the conversation or a session quote.

Complaints (the owner's decision, 2026-11-01): **a complaint is the second kind of handover, next to the lead.** The bot still doesn't solve complaints, repairs, refunds or legal questions, and promises nothing; it hands them to the team. A conversation is a support case (`_support_case()`) when the customer complains (`_COMPLAINT_RE`, or a fault in a unit "you installed") or `request_human_handoff` got a support reason — and stops being one once a sale starts (a `quote` exists). The `reklamacia` move apologises and asks for name, phone, e-mail and town (code adds the request if the reply forgot it, `_complaint_ask_text`; asked once, a later request in the reply is removed, and details sent later still get the question); `_consent_purpose()` then is `complaint`, so the canonical question is the complaint one from `consent_phrases.json`. Consent works as for a lead: the very next message, an explicit yes. `capture_lead` is the same tool for both and **the kind comes from the consent's purpose, never from the model**: `record["type"]` is `lead` or `complaint`, the event is `lead_captured` or `complaint_captured`, the line goes to `leads.jsonl`, the brief starts "# Reklamácia" (`_render_complaint_sections`: the customer's own messages, health terms redacted, no offer sections), the mail subject says "Nová reklamácia", with its own dedupe keys, and the auto-capture, notes after the handover, corrections and withdrawal apply alike. Before the record exists the reply may not say the case was handed over (`_PROMISE_RE`, `slub-bez-suhlasu`). A refusal stores nothing and gets the company contact (`_complaint_contact_text`, `COMPANY_EMAIL` / `COMPANY_PHONE`). Consent for one purpose doesn't cover the other: a sale after a written complaint closes the complaint (`_close_complaint_for_sale`, its mail goes out, `complaint_closed_for_sale`) and starts clean with the sales question. Both audits require the matching purpose. Like leads, complaints stay on the server unless the PM mail is set up (the owner, 2026-11-01). `request_human_handoff` still notes the request in `handoff_queue.jsonl` (without personal data); nothing reads that file, and the complaint reaches the team only through `capture_lead`. Its `purpose` is required; the fallback guess (`_SUPPORT_REASON_RE`) uses whole complaint terms only, so "installer", "vrátane" or "podporuje" stay sales. "Reklama" (an advert) isn't a complaint and "novú od vás" isn't a unit we installed (`_COMPLAINT_RE`, `_OUR_INSTALL_RE`); "vaša firma mi … montovala", "už som to hlásil" and "chcem opravu" are complaints (the QA of 2026-11-09 recorded one as a sales lead under sales consent).

GDPR refusal path: if the customer refuses, code records `consent_refused`, masks the personal data known by then in the whole session log (`_scrub_session_log`) and drops the `lead_*` fields from the state; the bot **does not call `capture_lead`** — no JSONL line, no Markdown file. It gives the customer the direct contact (`COMPANY_CONTACT`) and offers an in-chat recap. See sekcia 3 and 6 of the handoff rule.

### Pricing rules

The model never handles a price as input. `quote(items=[{code, qty}], segment, budget_eur, promotion_code)` takes model codes only and does everything else in code: looks up catalog prices, maps each product to its discount category, adds the segment modifier and an active, in-date promo (`active_promotions.promotions[]` matched by `code` + `applies_to` category), caps at `max_total_discount_pct` (the cap is never put in front of the model), and returns line items (incl. `unit_discount_eur` and `availability` from `stock_policy.json`), totals, `DPH_23pct_eur`, totals with DPH, the `recycling_fee_per_unit` (with the number of units and `total_min_eur` / `total_max_eur` for all of them — the bot used to multiply it itself), an `installation` note (no figure), a budget comparison (`budget.status` in the wording of the matematicka-kontrola rule, on the customer's basis: units with DPH unless they said "bez DPH", `compared_price_eur`; `budget_includes_installation` when their budget covers installation — then only the units can be said to fit), `comparison_with_earlier_quotes` (signed differences, which is cheaper and `reads`, the same as a whole sentence naming both offers by product with their totals — "než 1. ponuka" came back as "Poradie 1", and the offer moves tell the model to use that sentence: a price under the other product's name and a comparison the wrong way were 7 rewrites in the API run of 9657449) `together_with_earlier_quotes` (a multi-split and a separate set of one brand quoted in the same turn are one variant: their sum, so nobody adds it up or says the tool gives no total) and `cheaper_alternative` (a cheaper suitable single-split set when the customer named no series; for a multi-split, the same outdoor unit with the cheapest same-size wall indoor units of its price list, Wi-Fi as standard if wished, as `items`, `_cheaper_multi_indoors`); with one, or a fit warning that the set isn't the cheapest, `not_the_cheapest` says plainly not to call it that (`najlacnejsie-tvrdenie`, 7 rewrites in the API A/B of 2026-11-08). **No installation price exists anywhere** — not in `discounts.json`, not in `quote`, so any installation figure in a reply fails the provenance check. Every successful result is appended to `S().quotes`. A sanity guard rejects any unit price below 55 % of catalog as a policy-data bug — preserve it.

**A customer's false claims** (section "What the customer claims about the offers", QA 2026-11-03, `docs/qa_toshiba_haggler_2026-11-03.md`): when the message arrives, `_false_customer_claims()` checks it against the session's quotes — the dearer offer called the cheaper one (`_THAN_RE`, each side found by an amount it states, else a series, else a brand), an amount put under another product, "1 107 € je bez DPH" for a total with DPH, a difference no two offers have, an amount the customer says the bot wrote that no reply wrote (an echo of the customer's own number doesn't count) and a DPH rate other than 23 % (`VAT_PCT`). The facts go into the server context (`_claims_note`, `Session.turn_claims`, event `false_claim`); a concession that turn — "máte pravdu", "moja chyba", "som uviedol … nesprávne", "dobrá voľba" — is the HARD rule `ustupok` (`_CONCESSION_RE`); a final reply that states none of the facts' amounts gets them from code up front ("Na spresnenie: …", `false_claim_corrected`); a note after the lead that a claim contradicts is stored with the server's check beside it (`_after_note_line`). The price never moved in the QA; the bot agreed with false facts, admitted mistakes it never made and once said "dobrá voľba" to "SHORAI je lacnejšia". Two more HARD rules: a DPH rate other than 23 % (`dph-sadzba`, `_wrong_vat_rate`; the summary and the state get it rewritten, `_fix_vat_rate`) and "this series has no bigger size" when its price list does (`rad-velkost`, `_false_size_claims`). A discount the customer says applies or asks for on top (Black Friday, a company, quantity, cash or loyalty discount, `_DISCOUNT_CLAIM_RE`) and a promo code that isn't active (`_promo_codes`, `_find_promotion`) get a server-context note to say plainly that there is none — from `discounts.json`, without its percentages; the bot used to answer "zohľadním to" and "nemôžem potvrdiť". A sentence that points to the consent question ("odsúhlaste otázku nižšie") is dropped when no question follows (`_QUESTION_BELOW_RE`). A series called not sold ("Značku HAORI nepredávame") is `mimo-katalogu`. **Brands the customer rules out** ("Samsung nechcem", "Toshiba alebo nič", "iné značky ma nezaujímajú", `_excluded_brands`) are left out of the code-picked offers and the cheaper alternatives (`_customer_brands`), and the server context says not to offer them, until the customer asks for that brand again.

**The customer's latest word** (section "What the customer stands by now", the customers of QA 2026-11-02): the customer's messages are never edited, but `_facts_of()` and `_places_of()` read them in order and blank what a later message took back, and everything that sizes or classifies reads the result — `_facts_text()` / `_facts_inputs()` for areas, `_place_text()` for the kind of place — never `_all_user_text()`. Rooms: a room given a new size keeps only that one; "25 m2, nie 20" and "vlastne 25 m2" replace a number; "detskú vynecháme", "zabudnite na obývačku", "len spálňa", "stačí spálňa a obývačka" drop rooms (not "keď len obývačka?", a question; not "najprv spálňa, potom obývačka"), "predsa len pridajme" and "všetky izby" bring them back; a list is read by position ("Spálňa a obývačka, 14 a 28 m2"). A number with no room beside it, as big as the named rooms together, was the whole flat ("možno 60 m2"), and what stays keeps a unit ("obývačka 25" read as an area only beside a figure with one). Places: a denial ("žiadny salón", "salón nebude") counts at once; another place named later replaces a salon or a shop; a hall, wine cellar or hotel goes on a denial or a change of mind (`_CHANGE_OF_MIND_RE`); a server room only on a denial; named again, it is back. "Zabudni na všetko" starts clean. Of "the cheapest" and "the best" the later wish stands (`_OPPOSITE_WISHES`), and of one outdoor unit and separate sets too. What code recognised goes into the server context (`_changes_note`). The rules are narrow on purpose: what they don't recognise stays, as it always did.

**Fit check** (`_fit_check`, thresholds in `sizing_policy.json`; rules point there instead of restating numbers): `quote` checks a set against what the customer typed, never model-written state. It returns errors — overridable with `override_reason` only where the reference says so (oversizing only when the customer asked for more power, typed a kW figure or a code); technical impossibilities never (`_commercial_combo_errors`, `_accessory_errors`) — or `fit_warnings`: the place, oversizing and undersizing by `kw_per_m2` / `undersize_ratio` (an undersized set the customer chose by kW or code is a warning, `undersized`), the indoor unit type (wall is the standard), colour, Wi-Fi, filtration, "the best" and feature wishes, multi-split compatibility and outdoor size, the cheapest suitable set (`not_the_cheapest`, `cheaper_alternative`) and the customer's own budget. The same section covers the offers code picks and re-picks (named series, features, quiet and cheaper re-picks, multi-splits per room) and the readers every sizing decision goes through: `_customer_m2()` and `_customer_rooms()`, never `_all_user_text()`. Full reference: [docs/fit_check.md](docs/fit_check.md).

The PM brief also states facts from the customer's own words when the model didn't store them: the budget (`_customer_budget`, with "vrátane montáže" / "s DPH" scope), the m² and the conversation language (a Czech customer is "cs (bot odpovedal po slovensky)"). The `capture_lead` hallucination guard checks only code-like tokens (`_HANDOFF_CODE_RE`, with a stop-list for "DPH 23", "WIFI 09", "cca 17"), so descriptions next to codes in `interested_in` are fine.

`discounts.json` holds the whole pricing policy: `category_discount_pct` (one percentage per category, the same for both brands — every category 10 % and no B2B extra since 2026-10-20, the owner's decision, so every chat price is exactly 10 % off), `customer_segment_modifiers`, `active_promotions` and `recycling_fee_eur_per_unit`. It's loaded once at import; `_check_pricing_policy()` raises `SystemExit` if a category is missing, a percentage is outside 0–100 or a promo names an unknown category. Segments with `verification_required` (dealer, installer, wholesale) are refused by `quote` and left out of its schema enum (`CHAT_SEGMENTS`) — a salesperson verifies them.

Resolving a code to a price, without touching the data files:
- **Sets:** `_SETS` maps each set's code pair (from `set` strings or `indoor`+`outdoor`) to its record; requested pairs get `set_price_EUR`. A lone code that belongs to a set is refused unless a multi-split outdoor is in the request and the code is in that outdoor's own price list (a Samsung multi outdoor once let a lone Toshiba single-split outdoor through, sold as a "set"). Units of two brands in one call are refused too: one quote is one system of one brand, so each variant gets its own quote and its own total.
- **Role-aware price:** `_unit_price()` picks `indoor_price_EUR` / `outdoor_price_EUR` by the code's role. The index's own `catalog_price_eur` takes the first price key found, which gives CAC outdoor codes their indoor unit's price — don't use it for quoting.
- **Multi-split:** when a request contains an outdoor with `max_indoor_units`, indoor units are priced from the same price list as that outdoor and `check_compatibility` runs automatically (an incompatible combination is an error). A successful multi-split quote also counts as a compat check for the multi-split validator guard. One multi-split system per call, or N identical ones (outdoor qty N, every indoor count divisible by N; one system is checked); two different multi outdoors in one call are an error.
- **Ambiguity:** a code with more than one distinct price is an error listing the options — never a silent pick.
- **Discount categories:** `_discount_category()` is brand-neutral. `code`-role records (non-units) are `panels` if their section path contains "panel", `controls` if it matches `_CONTROLS_RE` (controllers, remotes, sensors, Wi-Fi, BMS, central), else `accessories`. Units are categorized by the folder they sit in: `single_split_sets` (priced as a set) / `single_split_units`, `multi_split_outdoor|indoor`, `commercial_outdoor|indoor` (`model` rows are outdoor units). All 742 priced records map; the categories are listed in `DISCOUNT_CATEGORIES`.
- **Availability:** `_availability()` from `stock_policy.json`: a code in `non_stock_codes` or matching `non_stock_code_patterns` makes the line non-stock, else the brand default (Toshiba stock, Samsung "PM confirms"). The non-stock rule file refers to the field.
- **RAV set prices** (`set_prices` sections in `rav_indoor.json`, keyed `models`) aren't indexed; `quote` prices RAV units one by one. The catalog sets include the RBC-ASCU32Y-E controller (and the panel for cassettes), so the bot must add those codes — the kazety rule says so.

**Price provenance check** (`_untrusted_amounts` in the validator): **every** euro amount in a reply — `1 290,50 €`, `€ 1 290`, `€3,500`, and the lower bound of `800–1 200 €` — must be within ±1 € of a euro-valued field (`_euro_fields()`: numbers under keys containing `eur`) of a `quote` result in `S().quotes`, of a euro amount the customer typed (`_customer_amounts()`: a whitelist — a number next to a currency, or after a budget/price word and not followed by a unit, or judged or compared as a price — "a 5000 je drahé", "3x 895 je menej ako 3564", `_PRICE_JUDGED_AFTER_RE`, `_PRICE_COMPARED_BEFORE_RE` — so `32 A`, `20 m²` or an IČO never count), or of a code-verified difference / sum of same-basis quote totals (or of a total and a customer amount). A three-quote combination (a + b − c, d03) counts only as a difference: written as a price ("Cena: …") it's an unquoted variant (`_combination_prices`). There is no minimum amount and no installation exemption; an amount written with cents must match to the cent. On top, an amount must belong to the product it is written next to (`_misattributed_amounts`: per paragraph / table row, the named series — `_SERIES_PATTERNS` — codes or brand must match the quote the amount comes from; a price line that names nothing belongs to the block right above it) and its DPH label must match the field it comes from (`_vat_mislabeled_amounts`). Prices from `search_knowledge` / `lookup_product` don't count (catalog, pre-discount), nor does the conversation summary. Any `~` / `cca` / `okolo` / `približne` before an amount or a range is flagged too. Both are HARD violations for the output gate. There is no calculator tool — it was removed so the model has no way to do price math.

Samuel Malíšek Klimabot does **not** offer the hidden 2% negotiation buffer — the `negotiation_buffer` block was removed from `discounts.json`. If a customer haggles beyond the computed discount, the bot politely declines and offers a cheaper model or human handoff.

`category_path` always starts with the capitalized brand from the directory name (`knowledge/samsung` → `Samsung`); `_brand_from_dir()` and `_record_product()` keep these aligned. `category_path` here is the price-list section path, not the discount category.

### Product index

`_build_product_index()` walks every brand JSON at startup (`brand_dir.rglob('*.json')`, skipping `*glossary*.json`) and registers every model code under fields `set/model/indoor/outdoor/code` (`code` covers panels and accessories). Set strings like `"AR70H09CAAWNEU + AR70H09CAAWXEU"` are split on space/`+`/comma — **never on `/`** because Samsung suffixes like `/EU` are part of the code. `_code_specs()` splits the price lists' "20/55" into `indoor_noise_min_dB` and `outdoor_noise_dB` and leaves the raw pair out of the result: it was read as a range from quiet to full power. Toshiba's "19/--/42" (low/mid/high) adds `indoor_noise_min_dB` and `indoor_noise_max_dB`, and so does the Samsung multi-split wall units' `noise_indoor_high_low_dBA` ("36/19", every size of every series), and the Samsung multi-split cassettes', ducts' and consoles' `noise_indoor_high_mid_low_dBA` ("35/31/27", high/mid/low), the only figures not from a price list: taken from Samsung's product pages on 2026-11-08, the URL in each record's `noise_source` and the file's `metadata.noise_note` (the black Premiere Plus isn't listed there and carries the white unit's figures, the same unit — the owner, 2026-11-08). `lookup_product` falls back to stripping `/EU`-style region suffixes, then a real code inside other words ("Toshiba RAS-2M10G3AVG-E"), then a unit type (`_type_units`, `_UNIT_TYPES`: "Toshiba kazetová 2,5 kW" → the matching residential single-split sets, residential multi-split indoor units — the residential cassettes are only there: Toshiba 1-way FLAT and 60x60, Samsung WindFree Mini 4-Way and 1-Way — and commercial RAV / CAC units, each with `outdoor_options` — the three smallest big-enough multi-split outdoors of the brand, or the same-size commercial outdoors — plus `panel_options` read from the series' `required_panel(s)` (`_series_panels`) and `controller_options` (`_CONTROLLER_OPTIONS`); "multi-split" / "FJM" with no other type → the residential multi-split wall units, with `wifi_standard`, `outdoor_by_rooms` (the smallest outdoor unit for 2–5 such units) and filtered by a named series — "Samsung Comfort" names Comfort S2 — the kW being one indoor unit's; a size the type doesn't have returns the next size up of each brand and kind (every size when there's none), and "RAV / CAC / komerčná" or "RAS / FJM / multi / domácnosť" narrows the kind), then a brand and a size, with or without "kW" (`_brand_size_sets`: "Samsung 1.4 kW" → that brand's wall sets in the smallest size that covers it, cheapest first, with `wifi_standard` and `filtration_tier`; "Samsung WindFree 2,5" narrows to the WindFree series), then a series name (`_series_sets`, `_SERIES_PATTERNS`: "HAORI 2,5 kW" → the exact set codes of that series, filtered only by a size in kW — "DAISEIKAI 10" is a name — with each series' listed `series_features`, so the model states features as the catalog does, and each set's SEER, SCOP and noise), then a fuzzy prefix match. `PRODUCT_BY_CODE` keeps a code's first record, for a wall unit often the multi-split row without SEER, so `lookup_product` and `compare_products` add `_code_specs()`: SEER, SCOP and noise from all its records (a Toshiba outdoor unit's from the acoustics tables, `outdoor_noise_cool_dB`), plus `sold_as_set`. `_set_specs()` gives every set of `_series_sets` and `_brand_size_sets` the noise of both units, so a comparison has figures for both brands. A bare size ("Samsung multi-split 2.5") narrows `_type_units` like one in kW (`_SIZE_BARE_RE`). A type asked for in a size it lacks returns the nearest size from 85 % up ("podstropná 4 kW" → 3.6 kW). The prompt sends the model there for set codes instead of `search_knowledge`.

`check_compatibility` validates two FJM/multi-split rules: indoor count ≤ `max_indoor_units` and combined cooling kW ≤ 176% of outdoor kW (Samsung spec).

The pair `user_input` + `assistant_reply` produces a complete conversation transcript — essential for GDPR/ÚOOÚ audit (you can prove what the bot asked, what the customer answered, and whether explicit consent was given).

Every API call is logged as `llm_turn`, including the side calls — `stop_reason` is `hyde`, `summary`, `regen_discarded` or `max_tokens_retry` for those (`_record_usage()`), and they are charged to the session too (`input_tokens`, and `cost_usd`, logged as `usd`), so the conversation cap and the web demo's daily budget see all spend. `cost_report.py` adds up the `usd` each `llm_turn` logged, so a conversation keeps the price of the model that ran it (logs without `usd` are priced as Haiku 4.5 from `model_prices.json`); its safety section counts `limit_hit` events by limit, and "Reply quality by commit" gives per deploy the turns, seconds per turn (median, p90), model calls and regenerations per turn and their top rules — `turn_end` and `session_start` carry `commit` (`COMMIT`: `KLIMABOT_COMMIT`, which `make build` passes into the image as a build arg, else `git describe --always --dirty`, else "unknown"; logged since 2026-11-07). It also runs a **GDPR compliance audit**, independent of the bot's own `consent_recorded` event and using the same `consent_phrases.json`: a lead is `ok` only if an `assistant_reply` showed the canonical **sales** question, the very next `user_input` said an explicit yes (and no refusal), and only then `lead_captured`. A complaint is audited the same way, against the complaint question (`complaint_captured`). A handover before the yes, after a paraphrased question, or with consent for the other purpose is a `violation`; sessions with `lead_captured` but zero `assistant_reply` events (pre-2026-05-13 logs) are `unverifiable` (audit gap, not a violation). Over the first eval run it flags exactly the four leads the reviewers found (c01, c12, c14, c18). Other sections: conversion funnel, lead quality, daily rollup, tool call distribution, safety/errors, reply feedback (thumbs in the web chat, with the replies rated down), averages. The web app shows the same report at `/admin`. Run with `-o` / `--output PATH` to also save to `reports/cost_report_<YYYY-MM-DD>.txt` (default path) or to a custom path; `reports/` is gitignored due to PII.

### Conversation summarization

`maybe_summarize()` triggers when the conversation has more than `HISTORY_MAX_USER_TURNS` (15) customer messages — tool rounds don't count, the history is cached anyway — or is longer than `HISTORY_MAX_CHARS` (200 000 characters): summarize the head with Haiku, keep last 14. The cut point is advanced forward to the next `user` message so `tool_use`/`tool_result` pairs are never split across the boundary — preserve this invariant when editing.

### HyDE expansion

`expand_query()` calls Haiku once per query to write a hypothetical answer, concatenated with the raw query before retrieval. Skipped when the query is already specific (>6 words OR matches `_MODEL_CODE_RE`); deduped via `_HYDE_CACHE` (process-wide, the 2 000 most recently used queries). Adds ~1s and a few hundred tokens per non-trivial turn. Finished searches are cached process-wide too (`_SEARCH_CACHE`, the 500 most recently used `(query, k)` pairs, logged with `cached: true`), but only when the HyDE expansion ran normally — one skipped for a conversation's budget or an API error isn't shared.

### Web app (`web/`)

A Flask + SSE app that wraps `bot.py` for interactive debugging in a browser. Layout:

- **Header**: brand + the conversation's API cost ("Rozhovor: 0,034 $", `session_usd` from `turn_complete` / `done`; debugging only) + the "Ladenie" switch + "Nová konverzácia" (confirmed in a `<dialog>`; `/api/reset` replaces the visitor's `Session` with a fresh one, new log file). In demo mode a strip below it (an `<aside>` landmark) warns visitors to use made-up personal details.
- **Customer view**: the header's "Ladenie" switch shows tool chips, server notices and the left sidebar; without it the visitor sees only the chat and the PM record. It is off by default when `/api/config` says `demo`, on otherwise; `?debug=1` / `?debug=0` override, and the visitor's choice is kept in `localStorage`.
- **Left panel "Poznámky bota"** (debugging only): live `CUSTOMER_STATE` rendered as a definition list. Fields are sorted by importance (lead_* → consent_* → place_* → segment → model_* → predpriprava_* → outdoor placement → features → other).
- **Center**: chat in a centred column. An empty conversation shows a welcome card with example questions (`.suggestion`, one click sends). Bot replies are rendered as sanitized Markdown (bold, lists, tables); user messages as plain text. While the server prepares and checks a reply, a typing row shows what is happening in customer words (`TOOL_LABELS`: "Počítam cenu…" for `quote`). Tool calls are small indigo chips (debugging only). The composer counts characters near `max_message_chars` and shows the messages left near `max_turns` (both from `/api/config`); the visitor can type while the bot answers. New content is followed only when the visitor is at the bottom, otherwise a "Nové správy" button appears. Under a reply that states a quote's total the chat shows a price card (`quote` event; the discount as a percentage — one rate, or the overall rate plus each line's rate when categories differ — and a "Toto chcem" / "I want this" button that sends "Chcem túto ponuku: <lines> — <total> s DPH." as the customer's message); under the consent question two buttons (`quick_replies`); under every bot reply 👍 / 👎, sent to `POST /api/feedback` and logged as `reply_feedback` (rating, reply number, a 300-character excerpt; 30 per network per minute).
- **Right panel "Zápis pre projektového manažéra"**: an empty state until `capture_lead` fires, then the handoff Markdown as a document card with a "Pripravený" badge and Copy / Download (.md) buttons.
- **`/admin`**: today's demo spend, open conversations, leads, GDPR violations, reply feedback and the full `cost_report.py` report over the logs in the data dir (conversations without a customer message are left out). Off (404) unless `KLIMABOT_ADMIN_TOKEN` is set; HTTP Basic auth with any user name and that token as the password (compared in constant time, 20 tries per network per minute); `Cache-Control: no-store` like `/api/history`, both carry personal data.
- **Narrow screens (< 1024 px)**: one panel at a time, switched by tabs under the header (Rozhovor / Zápis pre PM / Poznámky); a new PM record puts a dot on its tab and shows a toast. Light and dark themes follow the OS (`data-theme` on `<html>` overrides).
- **The on-screen keyboard**: the page never scrolls; `body` is a fixed box that `fitViewport()` sizes to the visual viewport (`--app-height`, `--app-top`, `html.vv`), because iOS Safari only shrinks and pans the visual viewport when the keyboard opens and would leave the header above the screen and the composer under the keyboard (Chrome on Android resizes the layout too: `interactive-widget=resizes-content`). A visitor reading the latest message stays on it, but the welcome card opens at its top (the first deploy scrolled a short phone past its heading); pinch zoom leaves the layout alone. While the keyboard is up (`html.kb-open`: the visible height under 75 % of the tallest at that width, touch screens only) the tabs make way; the demo notice stays. Keyed to the keyboard, not the focus: a tap blurs the message box before its click, and tabs reappearing then moved the consent button from under the finger (the first browser run caught it).

`bot.py` exposes a `run_user_turn_streaming(user_input)` generator that yields `(event_name, data)` tuples — used by both the CLI REPL (`_run_cli_repl`, kept under `if __name__ == "__main__":`) and Flask SSE. Event types:

| Event | Payload | UI handling |
|---|---|---|
| `token` | `{text}` | the checked text of one LLM response → bot bubble |
| `notice` | `{text}` | yellow center-aligned chip |
| `tool_call` | `{name, input}` | indigo chip between bubbles |
| `tool_result` | `{name, is_error, output_preview}` | mark previous tool chip red if error |
| `state` | full `CUSTOMER_STATE` dict | re-render left sidebar |
| `handoff` | `{markdown, path}` | render the PM record panel (sanitized Markdown) |
| `turn_complete` | `{input/output_tokens, cache_*, stop_reason, session_total, session_usd}` | next text starts a new bubble |
| `error` | `{message}` | red error chip |
| `quote` | `_quote_card()`: lines, totals, fee, budget — formatted by code | price card under the reply; sent at the end of the turn for each quote of the turn whose total the shown reply states (`_quotes_in_reply`) |
| `quick_replies` | `{kind: "consent", options: [{text, kind}]}` | buttons under the consent question; removed by the next message |
| `done` | `{session_tokens, session_usd, messages}` | end of one user turn |

A new tab calls `POST /api/session` and sends the returned id as the `X-Session-Id` header (a header, not a cookie, so it also works inside iframes such as a Hugging Face Space); the id is kept in `sessionStorage`, so a reload of the same tab resumes the conversation: the page fetches `GET /api/history` — the events this tab was shown (`Visitor.transcript`, `TRANSCRIPT_EVENTS`, rolled back with a cut-off turn, at most 1 500) — and replays them through the same handlers. `web.py` keeps a `Visitor` per id in memory (max 300). A conversation is finished — `bot.end_session()`, which also mails its lead — when its tab closes (`navigator.sendBeacon` on `pagehide` → `POST /api/end`, the id in the body because a beacon can't set headers; skipped when the page goes into the back/forward cache), but only after `END_GRACE_SECONDS` (20) in which any request from the same id (the reloaded page) cancels it; also after `KLIMABOT_IDLE_MINUTES` (30) without a message (a sweeper thread checks every 5 s; a reply still being prepared is never ended), or when the app shuts down (an `atexit` hook; SIGTERM is turned into a normal exit). When the registry is full, only visitors quiet for 10 min may be dropped, otherwise a new session gets 503; `bot.end_session()` always runs outside the registry lock. `web.py` holds a per-visitor lock so one turn runs at a time, and rolls back the conversation if a stream is cut off mid-turn (a dangling `tool_use` would break the next API call). The lock is released via `Response.call_on_close`, which runs even if the client disconnects before the stream starts.

Public demo: the limits are **on by default** (`KLIMABOT_DEMO=0` turns them off for local debugging) — messages per session (`KLIMABOT_MAX_TURNS`, 25), message length (800), request body 16 KB, new sessions per network per hour (40, a Reset counts too), messages per network per minute (15), 2 turns running per network, 6 turns running in total (`KLIMABOT_MAX_CONCURRENT_TURNS`), and two daily USD budgets (UTC day): per network (`KLIMABOT_IP_DAILY_USD`, $2) and across all visitors (`KLIMABOT_DAILY_USD_BUDGET`, $5). A network is an IPv4 address or an IPv6 /64. Before a turn `web.py` reserves the most it may cost (`TURN_USD_CAP`, or what is left of the conversation's budget) and settles the real cost (`sess.cost_usd` delta) when the stream closes; the totals are saved to `.demo_spend.json` (networks as salted hashes, the salt changes daily) so a restart doesn't reset them. Refusals are logged as `limit <kind> net=<hash>`; error texts are generic and give `COMPANY_CONTACT`. `KLIMABOT_REPO_URL` adds a source link to the banner; `HOST`/`PORT` set the bind address. Behind a reverse proxy set `KLIMABOT_TRUSTED_PROXIES` to the number of proxies (1 on a Hugging Face Space): only then is `X-Forwarded-For` trusted, via Werkzeug's `ProxyFix`, which reads the hop those proxies appended — the rest of the header is client-controlled and would let anyone dodge the per-IP limits. State is in-process, so run a single worker process. These limits are a first line of defense — the Anthropic Console spend limit on the demo's workspace is the real backstop (and `bot.py`'s breaker turns hitting it into a polite offline reply). `web.py` calls `os.chdir(PARENT_DIR)` before `import bot` so relative paths (`knowledge/`, `config/`, `data/`) resolve from the project root regardless of where `web.py` is launched from.

The HTML/CSS/JS lives entirely in `web/static/index.html` (single file, ~1 650 lines, vanilla JS, design tokens as CSS custom properties). No build step. The look (2026-11-11): a cyan → blue → indigo gradient (`--grad-brand`, `--grad-primary`; no Samsung or Toshiba colours) over a soft aurora background, glass header and panels, Inter; every text colour 5:1 or more on its surface, white 5.4:1 or more on every point of the button gradient (axe can't measure text over a background image and marks it incomplete, not failed, so those pairs were computed by hand). Motion only for entrances and state changes, `--ease` / `--spring`: messages slide in from their side, price card lines in a stagger, the consent buttons pop, the avatar's ring spins and the step label shimmers while a reply is prepared, the PM record and the toasts come in and go out. Prices appear whole (nothing counts up: a frame of a count-up is an amount `quote` never produced), reduced motion turns everything off, and a conversation rebuilt after a reload doesn't replay its entrances (`.still`). marked and DOMPurify are pinned local copies in `web/static/vendor/` (version in the file name, SHA-256 checked against jsDelivr when added), and so is Inter (`inter-gf20-latin.woff2`, `inter-gf20-latin-ext.woff2`: Google Fonts' variable build v20, 133 KB, preloaded, served as `font/woff2` — `web.py` registers the type, the slim image's Python had none; SIL OFL in `inter-OFL.txt`); nothing is loaded from a CDN. `web.py` sends `X-Content-Type-Options`, `Referrer-Policy` and, on the page, a Content-Security-Policy that allows only the app's own origin (`'unsafe-inline'` because the UI is one file; framing allowed for a Hugging Face Space). To update a library: download the new version into `vendor/`, check its hash, change the `<script src>` and run the tests (`WebTests` checks that every script on the page is local and served).

## Conventions

- Slovak is the primary content language. Print messages, tool descriptions visible to the model, and system-prompt instructions stay in Slovak; Python identifiers and code comments stay in English.
- `claude-haiku-5-5` is used everywhere (main turn, HyDE, summarization), since 2026-10-30, with adaptive thinking on the customer turn (`TURN_THINKING`) and off on HyDE and the summary (`SIDE_THINKING`), and `output_config.effort` `EFFORT` (medium, Haiku 5.5's default, set explicitly) on every call, all sent by `_call_model()` (env `KLIMABOT_THINKING=off`, `KLIMABOT_EFFORT`; xhigh and max are refused at startup, the side calls can't turn thinking off there). Thinking on since 2026-11-05, after the Haiku 5.5 prompting guide (reasoning-like text in replies is more frequent with thinking off — what the gate cuts as `interne-info` and narration) and the CLI-vs-API comparison of 2026-11-01 (the CLI, which always thinks, needed half the regenerations); production had it off from 2026-10-30. The owner kept it on 2026-11-07 after an A/B on the real API (fce79ec without thinking against 77fe807, the same scripts in parallel, `eval/runs/ab_2026-11-06/`, gitignored): over 64 conversations regenerations 102 → 62, cut sentences 15 → 4, analyzer findings 39 → 22, the AI review 4.34 → 4.47, and on `direction.json` 0.20 → 0.08 regenerations per turn, at 1.7× the cost ($0.46 → $0.79 for the 64) and 5.1 → 8.6 s per turn, with leads and the GDPR audit unchanged. The extra cost is inherent: thinking output, and the cache re-writes caused by sending each tool round's thinking block back unchanged within the turn. The history keeps no thinking blocks, and thinking counts against `max_tokens`. The checklist also carries the guide's line for chatbots that the rules hold for the whole conversation, whatever the customer argues. It can refuse (`stop_reason: "refusal"`, no text): the gate treats that as an empty reply, and a refused summary leaves the history as it is. Don't introduce a different model without a reason.
- Files written by the bot at runtime, all under `KLIMABOT_DATA_DIR` (`DATA_DIR`: `data/` by default, `/data` in Docker; `cost_report.py` reads the same setting): `logs/`, `leads.jsonl`, `handoff_queue.jsonl`, `handoff_records/`, `sessions/`, `.kb_vecs.npy`, `.kb_hash.txt`, `.spend_breaker.json`, `.demo_spend.json`, `.lead_mail_sent.json`. All are gitignored (PII concerns for `leads.jsonl`, `handoff_records/`, `sessions/`).
- Web debugger dependency: `flask` (3.1+). Installed by `./setup_project.sh`. No other web-side dependencies — UI uses vanilla JS + local copies of marked and DOMPurify (bot replies and the handoff Markdown contain visitor-typed text, so they're sanitized before rendering).
- `knowledge/samsung/` and `knowledge/toshiba/` are real data transcribed from the manufacturers' public price lists (attributed in each file's metadata and the index headers; see README → Data). `knowledge/montaz/` is a mock sample and `discounts.json` is illustrative (a uniform 10 %, set by the owner on 2026-10-20). Keep the source attribution when updating the data.
- Rule files in `knowledge/rules/` contain no concrete euro amounts — the model could repeat them, and every amount must come from `quote`. Examples use output field names (`total_eur`, `total_with_DPH_23pct_eur`) and never an installation price. Likewise, sizing thresholds live only in `sizing_policy.json`, the filtration order only in `filtration_policy.json`, stock status only in `stock_policy.json` and the consent wording only in `consent_phrases.json`; rules refer to them instead of restating them. What the bot may claim about health, warranty and stock is in `knowledge/rules/feedback_schvalene_tvrdenia.md`.
- `consent_phrases.json` is marked as a draft: the wording and the legal basis (consent vs. Art. 6(1)(b)) still need the DPO's approval. Changing a question changes the audit too — older logs with the old wording no longer pass.
